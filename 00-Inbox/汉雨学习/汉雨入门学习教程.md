# 汉雨 HanRain 使用入门

## ——从认识一个“字”，到写出自己的关系程序

**适用阶段：** 字库、号库已经完成持久化并随汉雨发行包提供  
**面向对象：** 第一次接触汉雨的程序员、学生、语言使用者  
**教学目标：** 会查字、会用字、会传号、会连字、会定义自己的文字、会组织跨文件程序，并能读懂汉雨的主要错误信息

---

# 第一章　先不要学编译器：先学会怎样使用汉雨

学习汉雨时，最容易犯的错误，是一开始就去理解：

```text
FormalZi
Nature
Mandate
HaoBinding
RelationHan
RainCommit
三刀流
二人转
CFG
SSA
MIR
```

这些概念很重要，但大部分属于：

```text
编译器
字库
关系验证
运行时
调试和诊断
```

普通使用者第一天并不需要掌握。

你真正需要先记住的是六件事：

```text
名字
字
号
道路
关系
结果
```

可以先用一句话理解汉雨：

# **字做事，号往来，名字认字，道路找字，关系决定它们怎样共同完成事情。**

---

# 第二章　汉雨最重要的两个东西：字和号

## 2.1 什么是“字”

在汉雨中，“字”不是一个普通字符。

字是一个能够：

```text
接受东西
处理东西
保持自己的规则
产生结果
```

的计算主体。

例如：

```text
加
说
比较
读取
解析
排序
写入
转换
```

都可以成为成熟文字。

你可以暂时把字理解成：

> **一个知道自己能吃什么、会做什么、会吐出什么的计算单元。**

但字并不完全等同于传统语言里的函数。

因为一个成熟字还可以具有：

```text
状态
资源要求
失败方式
所有权要求
效果
公开端口
适用环境
```

因此“字”比单纯函数更接近一个有边界的自治计算者。

正式文字在验证完成以后会取得稳定身份，并进入字库；同一正式文字可以被不同名字引用，而名字变化不能随意改变文字本身的身份。

---

## 2.2 什么是“号”

号是字之间真正传递的东西。

号可以承载：

```text
整数
文本
布尔值
数组
文件
结果
错误
引用
资源句柄
能力
Generation
证明
```

所以：

```text
3
4
"你好"
一个文件句柄
一次计算结果
```

都可以在某场关系中成为号。

最简单的关系就是：

```text
号
↓
字
↓
新号
```

例如：

```text
3、4
↓
加
↓
7
```

在汉雨里可以把它理解为：

# **字吃号，字吐号。**

# 第三章　汉雨最重要的阅读方向

看到一条汉雨字句时，记住：

# **右边准备，中央处理，左边承果。**

例如：

```hanrain
和* 加 3，4；
```

可以读成：

```text
右边：

3
4

    ↓

中字：

加

    ↓

左边：

和
```

也就是：

```text
3、4
→ 加
→ 和
```

因此：

```hanrain
和* 加 3，4；
```

可以用普通话读成：

> “让‘加’吃下 3 和 4，把结果号叫作‘和’。”

这里的：

```text
加
```

是成熟文字。

```text
3、4
```

是输入号。

```text
和
```

是当前源码给结果号起的名字。

源码本身仍然正常从左到右解析；“右吃左吐”描述的是字句内部的数据关系，而不是要求编译器把整个文件倒着读取。

---

# 第四章　星号 `*` 怎么看

初学汉雨，先只记住两种最常用写法。

## 4.1 直接调用一个字

```hanrain
*说 文本；
```

读作：

> 让“说”吃下“文本”。

因为你并不需要保存“说”的返回结果，所以左侧没有结果名。

---

## 4.2 保存一个字产生的结果

```hanrain
和* 加 3，4；
```

读作：

> “加”吃下 3 和 4，把结果交给“和”。

因此可以记成：

# **名前有星，字开始做事；号后有星，左边接住结果。**

统一源码设计中，`*` 被收束为“当前字句的关系着力点”，而不再承担“特殊字等级”“动态对象”等额外含义。

---

# 第五章　持久化字库完成以后，为什么汉雨才真正好用

早期汉雨如果没有稳定字库，程序员会不断面对一个问题：

```text
“加”到底是谁？

“说”在哪里？

这个“解析”和那个“解析”是不是同一个？

换一个目录以后还能不能找到？
```

字库持久化完成以后，这些问题由工具链负责。

一个成熟字可以长期拥有：

```text
稳定身份
公开名字
长期能力
端口
失败规则
版本
语义道路
实现候选
```

使用者不需要每个项目重新制造“加”“比较”“字符串”“文件”等基础能力。

持久化设计本身也不是要求程序运行时不断查询一个大型数据库；汉雨一直坚持：

```text
源码名称
↓
编译期查字库
↓
NameID / ZiIndex
↓
直接调用 / SSA / 机器操作
```

静态确定以后，字库信息应尽量从运行热路径消失。持久化更接近“编译器注册表 + 快照 + 增量索引”，而不是业务数据库。

所以，对普通使用者而言：

# **持久化字库的意义就是：成熟文字已经在那里，你只需要找到它并建立关系。**

---

# 第六章　三种找字方式

持久化以后，可以把汉雨能够看到的文字理解为三层。

## 6.1 初路

初路是语言自己提供的最小基础集合。

例如某个版本中的：

```text
归
必要的关系闭合能力
基本字面量形成能力
最终冻结的基础控制能力
```

可以直接使用。

例如：

```hanrain
*归 和；
```

这里“归”并不是没有正式身份。

它可能真正拥有类似：

```text
初——控制——归
```

的完整道路。

只是语言已经替你把它放入最小可见集合。

所以：

# **通用字不是无名，而是其名已在初。**

初路应保持很小；文件、网络、终端、设备、线程以及一般平台能力不应全部偷偷加入初路。

---

## 6.2 项目常路

一个项目可以规定自己的常用道路。

例如某个数据处理项目可能长期使用：

```text
标准——文本
标准——集合
项目——数据
项目——日志
```

这些能力不需要每个文件重新配置完整环境。

可以把项目常路理解成：

> **这个工程通常生活在哪些语义地区。**

---

## 6.3 显式引路

如果当前源码要使用一个没有自动可见的正式名字，应明确写出：

```hanrain
引 标准——整数——加；
```

它只表示：

> 当前源码现在可以看见正式文字“加”。

它不会：

```text
重新创建“加”
复制“加”
修改“加”
改变“加”的能力
```

只是建立了一条可见关系。

---

# 第七章　语义道路不是文件路径

这是汉雨非常重要的一点。

假设存在正式道路：

```text
标准——整数——加
```

它的源码今天可能位于：

```text
src/std/int/add.mh
```

以后移动到：

```text
lib/core/arithmetic/add.mh
```

只要文字本身没有改变身份，它仍然可以继续是：

```text
标准——整数——加
```

因此：

# **道路回答“它是谁、从哪里找它”，目录回答“文件现在放在哪里”。**

两者不是同一件事。

这使项目重构时：

```text
移动文件
调整目录
重新分包
```

不必自动造成整个语义世界改名。

相关设计明确要求将：

```text
语义道路
物理文件
依赖关系
别名桥
```

分开维护，并在项目装载后将道路转换为稠密 ID，而不是让程序运行时重复比较中文路径。

---

# 第八章　第一次使用一个库里的字

假设你需要终端输出能力。

完整道路可能是：

```text
标准——终端——输出
```

可以引入：

```hanrain
引 标准——终端——输出 为 说；
```

以后当前源码中就可以写：

```hanrain
*说 "你好，汉雨"；
```

这里：

```text
标准——终端——输出
```

是正式道路。

```text
说
```

是当前源码中的局部称呼。

局部称呼不会给这个文字制造新的：

```text
正式身份
能力
版本
正文
```

只是让当前文件写起来更自然。

可以理解成：

```text
完整道路
≈ 正式姓名

当前称呼
≈ 当前语境里的称呼
```

# 第九章　你的第一个汉雨程序

为了教学，假设当前发行字库存在：

```text
标准——终端——输出
```

源码可以写成：

```hanrain
引 标准——终端——输出 为 说；

- 学习

    # 终端

        @ 问候

            *问好：
                *说 "你好，汉雨"；
```

先不要分析内部编译过程。

从用户角度只读四层：

```text
- 学习
这是这个源码单元的姓

# 终端
当前文字生活在终端能力域

@ 问候
这是向外公开的名字

*问好
这是当前名字内部的一段文字关系
```

最后：

```hanrain
*说 "你好，汉雨"；
```

就是实际工作：

```text
"你好，汉雨"
↓
说
↓
终端
```

程序入口不永久属于某个文字身份，而由构建配置选择，因此普通源码不需要为了模拟 C 语言而人为制造一个永恒的 `main`。统一源码方案将这一原则概括为：

# **源码立名，构建择始。**

# 第十章　姓、氏、名到底是什么

初学阶段可以用三个问题记住。

## 10.1 姓：这份程序属于哪个治理根？

写作：

```hanrain
- 算
```

姓主要回答：

```text
我属于哪里？
我的公共身份从哪里开始？
哪些东西默认与我处在同一治理边界？
```

不要把姓理解成传统语言里的 `class`。

也不要简单理解成文件夹。

---

## 10.2 氏：我在什么能力环境里工作？

写作：

```hanrain
# 计算域
```

氏可以代表：

```text
计算能力
资源环境
设备
Provider候选
ABI环境
效果边界
```

例如：

```hanrain
- 驱动

    # 网卡
    # 中断
    # 内存
    # 日志
```

这些氏默认是平级的。

缩进本身不意味着：

```text
网卡继承中断
中断拥有内存
日志自动取得网卡权限
```

有关系时应显式建立关系。统一源码设计也明确禁止把氏的缩进误解为能力、权限或 Mandate 的自动继承。

---

## 10.3 名：别人怎样认识这段文字？

写作：

```hanrain
@ 简单加法
```

名是面向公共世界的入口。

但要注意：

# **写下名字，不等于这个字已经合法存在。**

编译器仍需要检查名字下面的正文。

过程是：

```text
提出名字
↓
形成文字
↓
检查
↓
验证
↓
提交
↓
正式进入字库或项目注册表
```

这就是：

# **名先立其候，验文而后正名。**

正式文字形成与名字提交本来就是分离的；验证失败不能留下半成品正式字。

---

# 第十一章　定义自己的文字

假设字库已经提供：

```text
标准——整数——加
```

先引入：

```hanrain
引 标准——整数——加；
```

然后可以定义自己的“求和”：

```hanrain
- 学习

    # 计算

        @ 简单加法

            *求和 左 右：
                *加 左 右；
```

这里的：

```text
求和
```

是你在当前文字中建立的新名字。

如果它只是完整投影现有“加”的能力：

```text
输入相同
输出相同
效果相同
失败规则相同
```

编译器可以证明：

```text
求和
只是“加”在当前关系中的身份投影
```

最终甚至不需要多产生一层运行时调用。

如果你写：

```hanrain
*安全求和 左 右：
    *检查溢出 左 右；
    *加 左 右；
```

那么它已经加入新的：

```text
检查
失败关系
证明
```

这时它可能成为真正新的组合文字。

因此：

# **改名字不一定造新字；增加新的稳定关系结构才可能形成新字。**

---

# 第十二章　调用自己的文字

定义：

```hanrain
*求和 左 右：
    *加 左 右；
```

调用：

```hanrain
和* 求和 3，4；
```

执行关系是：

```text
3
4
↓
求和
↓
和
```

然后：

```hanrain
*说 和；
```

就形成：

```text
3、4
↓
求和
↓
和
↓
说
```

如果一切都是静态的，最终可能下降成普通机器计算与输出，不需要在运行时保留完整的姓氏名、字库、命契和关系对象。

这正是汉雨一直坚持的：

# **语义完整，机器从简。**

---

# 第十三章　连字：汉雨最值得掌握的写法之一

前面的写法：

```hanrain
原温* 读温 传感器；
摄氏* 转摄氏 原温；
文本* 加单位 摄氏；
*说 文本；
```

中间有：

```text
原温
摄氏
文本
```

这些名字有助于阅读和调试。

但如果关系已经明确，可以写得更紧：

```hanrain
*说 加单位 转摄氏 读温 传感器；
```

这叫做“连字”。

它看起来像几个字直接接在一起，但内部并没有删除号。

实际仍然是：

```text
传感器
↓
读温
↓ 隐藏号 h0

h0
↓
转摄氏
↓ 隐藏号 h1

h1
↓
加单位
↓ 隐藏号 h2

h2
↓
说
```

也就是：

# **连字省号名，不省号。**

公共关系内部仍然可以恢复成：

```text
字 → 号 → 字
```

而不是创造一种无法解释的：

```text
字 → 字
```

连字方案本身也明确要求，对多输出、所有权、错误、Generation 和效果顺序继续进行完整检查。

---

# 第十四章　什么时候应该连字，什么时候应该展开

适合连字：

```text
关系短
方向明确
中间结果只有一个
错误关系简单
没有复杂资源生命周期
```

例如：

```hanrain
*说 格式化 加 3，4；
```

更适合展开：

```text
存在多个输出
存在Result / Option
涉及资源所有权
需要观察中间结果
关系较长
存在多个合法端口
需要调试
```

例如：

```hanrain
原文* 读取 路径；
结果* 解析 原文；
报告* 校验 结果；
*说 报告；
```

经验规则：

# **读不清楚时，就把隐藏号重新写出来。**

这不是“低级写法”。

显式号名本来就是汉雨重要的解释与调试工具。

---

# 第十五章　连字不是传统函数管道

看到：

```hanrain
*甲 乙 丙；
```

不要简单认为它必然等于：

```text
甲(乙(丙))
```

汉雨还要检查：

```text
乙吐哪些号？
甲能够吃哪些？
当前究竟需要哪些？
所有权是否合法？
Generation是否新鲜？
失败出口谁接？
效果顺序是否允许？
```

如果右字吐出：

```text
正文
状态
错误
```

而左字有多个可能输入端口，编译器不能依靠书写顺序猜。

若不能得到唯一合法关系，就应该报错。

所以：

# **汉雨的连字是关系匹配，不是字符串式拼接。**

---

# 第十六章　一个名字可以有多个称呼

假设公共名是：

```text
简单加法
```

也可能允许：

```hanrain
@ 简单加法【加法】【sum】
```

其中：

```text
简单加法
是规范公共名

加法
sum
是别名
```

别名仍然指向同一正式文字。

它们不能分别拥有自己的：

```text
正文
长期能力
正式身份
版本
```

因此：

# **多名可以指一字，但不能因为换称呼就偷偷制造第二个字。**

---

# 第十七章　跨文件编程

假设文件甲公开：

```text
算——计算——简单加法
```

文件乙只需要：

```hanrain
引 算——计算——简单加法；
```

以后通过它的公开名字使用。

跨文件时遵守一个非常重要的规则：

# **源码引名，编译器据名取字；号循名字的端口往来。**

普通源码不能直接：

```text
拿另一个文件的局部号
访问另一个文字的私有状态
引用匿名实现内部
```

所以：

```text
跨文件复用的是公开文字
而不是偷取别人执行到一半的内部状态
```

同一目录也不自动意味着互相可见；可见性由公共名字、引路、常路和初路决定。

---

# 第十八章　什么时候应该新增一个正式字

持久化字库完成以后，用户最不应该养成的习惯是：

```text
每发现一个小功能
→ 往字库增加一个新字
```

汉雨更推荐：

# **组合优先，增字从严。**

如果一个需求已经能通过：

```text
现有成熟文字
+
连字
+
局部号
+
已有关系组合
```

清楚、稳定地完成，就没有必要扩大全局字库。

例如：

```text
读取
→ 解析
→ 校验
→ 输出
```

如果只是某个项目中的固定组合，可以先形成项目文字。

只有当某个能力具有：

```text
独立而长期稳定的语义
清楚的输入输出
稳定的失败方式
明确的公共用途
值得跨项目复用
```

时，才适合考虑成为新的正式基础字。

这样能避免字库逐渐膨胀成：

```text
几千个只差一点点的函数名字
```

而失去汉雨“以关系组合收敛能力”的优势。

---

# 第十九章　字库持久化以后，用户写下一个新字时发生什么

假设你定义：

```hanrain
@ 安全加法

    *安全求和 左 右：
        *检查溢出 左 右；
        *加 左 右；
```

用户看到的是源码。

后台可能经历：

```text
名字候选
↓
正文验证
↓
身份形成
↓
长期能力形成
↓
正式文字提交
↓
项目字库 / 注册表持久化
```

如果中间失败：

```text
类型不合
端口不全
资源违规
名字冲突
正文不完整
```

那么这个正式文字就不应该以“半成品”状态留在持久化字库。

既有生产路线明确要求：

```text
ValidatedZiText
→ Identity
→ Nature
→ FormalZi
→ NameEntry
```

形成一个可回滚的提交事务；任一步失败，都应恢复到提交前状态。

因此用户可以相信：

# **能在字库里成为正式字的东西，应当已经过完整形成。**

# 第二十章　错误信息应该怎样读

汉雨的错误最好先分成五类。

## 第一类：找不到

例如：

```text
道路不存在
名字不可见
没有引入对应公共名
```

先检查：

```text
道路是否正确
当前作用域是否可见
是否需要显式引路
```

---

## 第二类：字还没形成好

例如：

```text
名字已经提出
但正文验证失败
```

这表示：

```text
你已经给它起名
≠
它已经成为成熟文字
```

---

## 第三类：吃不下

例如：

```text
连字端口不匹配
类型不兼容
多输出无法唯一选择
```

典型诊断可以理解成：

```text
读温
吐出：原始温度

解析
需要：文本

失败：
解析 ← 读温

建议：
插入转换文字
或显式命名中间号
```

源码重整规范已经把精确指出“哪两个相邻文字无法连接”列为主要诊断目标。

---

## 第四类：关系没有资格发生

例如：

```text
资源不允许
所有权冲突
Generation陈旧
能力不足
效果不允许
```

这时候不要只问：

> “为什么这个函数不能调用？”

更适合问：

> **“为什么当前这场关系不允许成立？”**

这正是汉雨与传统函数调用思维最大的差异之一。

---

## 第五类：结果没人处理

例如一个字可能产生：

```text
成功结果
失败结果
```

如果失败没有被处理，编译器应该明确告诉你。

不要为了“让代码跑起来”而默默丢弃失败号。

---

# 第二十一章　Result 和 Option 怎么理解

初学时不需要把它们想得太复杂。

可以理解为：

```text
Result
这个关系可能成功，也可能失败

Option
这个关系可能有结果，也可能没有
```

汉雨更强调：

> 它们不是额外塞给你的“特殊类型语法”，而是关系可能产生的正式结果结构。

所以使用一个可能失败的文字时，要明确：

```text
成功以后谁接？

失败以后谁接？
```

发布路线已经要求 Result/Option 覆盖真实源码中的成功、失败、失败传播以及未处理失败诊断，并保持多后端语义一致。

# 第二十二章　你不需要手写“汉”和“雨”

虽然语言叫“汉雨”，用户源码里却不应该满篇都是：

```text
汉
雨
RelationHan
RainCommit
```

普通程序员更常写的是：

```text
字
号
名字
道路
控制
资源关系
```

编译器内部再负责判断：

```text
这场关系是否成立？
现在还有什么没有完成？
这次变化什么时候真正提交？
什么时候可以关闭？
```

因此可以这样理解：

```text
字和号
是你最常直接接触的东西

汉和雨
是语言替你守住关系成立与变化的机制
```

静态程序中，这些高层关系信息应尽可能在进入最终机器代码前消失。

# 第二十三章　三刀流和二人转，普通用户要不要学

第一周：

# **不用。**

你只需要知道：

当编译器面对多个可能方法时，它不会任意猜。

内部可能会进行：

```text
检查当前材料
↓
寻找合法方法
↓
判断当前模型是否充分
↓
准备关系
↓
最终提交
```

三刀流与二人转主要帮助语言完成：

```text
筛选
择法
证明
有限候选构造
准备
```

但它们不应该要求普通代码变成：

```text
乱刀 xxx
利刀 xxx
道刀 xxx
二人转 xxx
```

等你开始写：

```text
复杂系统
动态Provider
异步关系
资源仲裁
插件
运行时重绑定
```

再学习这些高级机制。

# 第二十五章　持久字库使用者的正确习惯

建议形成以下习惯：

```text
先查字
再造字

先连字
再封装

能用已有正式字组合
就不要扩大基础字库

跨文件只走公共名字

中间关系不清楚
就显式写号

名字歧义
就写完整道路

资源关系复杂
就少用过长连字

遇到错误
先判断是“找不到、吃不下、无权发生、还是结果未处理”
```

尤其不要形成：

```text
看到功能
→ 新增关键字

看到领域
→ 新增十几个正式字

看到关系
→ 新增一种号

看到特殊情况
→ 新增运行时对象
```

汉雨真正希望得到的是：

# **较小而稳定的字库，配合丰富但可证明的关系组合。**

# 第二十七章　从传统语言迁移过来的程序员怎么转换思维

## 如果你来自 C++

```text
一个正式文字
+

+
某个当前关系
```

## 如果你来自 Python

不要因为语法可以很短，就认为关系也是动态猜出来的。

汉雨希望：

可以把：

视为非常熟悉的思想。

# 第二十九章　但你必须知道三个底层承诺

即使不学内部架构，也建议使用者知道汉雨向你作出的三个承诺。

## 承诺一：身份不能乱漂

文件移动、别名改变和普通重构，不应无缘无故把一个成熟文字变成另一个文字。

---

## 承诺二：关系不能靠猜

存在多个合法绑定时：

```text
报歧义
```

而不是：

```text
挑一个看起来差不多的
```

---

## 承诺三：静态能证明，就不留运行时税

例如：

```text
姓
氏
名字字符串
道路
静态命契
连字证明
```

如果已经完全确定，就应该逐步下降成：

```text
直接调用
SSA值
跳转
地址
机器指令
```

而不是每执行一次都重新解释中文语义。现有源码与持久化设计都明确以这种静态擦除作为性能底线。

# 第三十章　最终心智模型

学完入门以后，只要能够在脑中形成下面这张图，就已经掌握了汉雨最核心的使用方法：

```text
                    字库
          成熟文字已经持久存在
                     │
                 沿道路取字
                     │
                     ▼
号 ───────────────→ 字
材料、值、资源       │
                     │ 吃下
                     │
                     │ 处理
                     │
                     ▼
                 新的号
                     │
                     ├── 给下一字
                     │
                     ├── 成为结果
                     │
                     └── 进入新的关系
```

多个文字再通过号组成：

```text
号
↓
字
↓
号
↓
字
↓
号
↓
字
↓
结果
```

源码可以进一步把中间号名省略：

```text
字 字 字 字
```

但编译器内部仍然知道：

```text
谁吐了什么
谁吃了什么
为什么能吃
谁拥有它
失败怎么办
什么时候关系真正成立
```

这就是汉雨。

# 三十一章　一句话记住汉雨

如果只留下最核心的五句话：

> **名字让我们知道是谁。**

> **道路让我们知道去哪里找。**

> **字负责做事。**

> **号负责让字彼此发生关系。**

> **关系明确以后，编译器把复杂语义尽可能还原成简单机器行为。**

再压缩成一句：

# **名认其字，路寻其身；字食其号，号通其间；关系有据，终归于机。**

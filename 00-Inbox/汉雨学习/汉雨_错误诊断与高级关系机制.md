# 汉雨 HanRain《错误诊断与高级关系机制》

## ——先判断哪条关系无权继续，再追问为什么；错误不是旁路，而是关系事实的一部分

**文档性质：** 进阶用户手册 / 高级关系机制说明  
**适用阶段：** 已完成《源码语言教程》《字库使用手册》《关系编程教程》，开始处理复杂项目、系统软件、动态运行时、资源治理或编译器扩展  
**主要读者：** 汉雨应用开发者、标准库作者、系统开发者、运行时开发者、编译器维护者  
**本文目标：**  
1. 建立统一的错误诊断方法；  
2. 从“表面报错”追踪到“哪一场关系为什么不能继续”；  
3. 解释 FormalZi、Nature、Mandate、HaoBinding、Generation、三刀流、二人转、汉、雨等高级机制；  
4. 保持公开源码、关系治理、CFG/SSA、唯一 HanRain MIR 与后端之间的权威边界。

> 本册把原计划的《错误诊断手册》和《高级关系机制》合并。  
> 原因很简单：汉雨中的高级机制，最容易通过“为什么当前关系被拒绝”来理解；错误诊断也只有理解关系权威链后，才能真正做到可解释。

---

# 第一编　先学会看错误

# 第一章　汉雨错误的核心问题不是“哪里报错”

普通编译器错误常问：

```text
哪一行？
哪个类型？
哪个变量？
```

汉雨还要继续追问：

```text
哪一场关系？
哪个字？
哪个号？
哪个端口？
哪个道路？
哪个本场许可？
哪个Generation？
哪条生命周期义务？
为什么当前关系无权继续？
```

因此：

# **汉雨诊断的目标不是只指出“错了”，而是说明“为什么当前关系不能继续”。**

---

# 第二章　所有错误先分成六类

普通使用者遇到问题时，优先分类：

```text
1. 找不到
2. 没形成
3. 吃不下
4. 无权发生
5. 结果没人接
6. 生命周期不允许
```

这六类覆盖了大多数用户级问题。

---

# 第三章　第一类：找不到

典型表现：

```text
名字不存在
道路不存在
名字不可见
别名失效
版本迁移
```

例如：

```hanrain
结果* 加 左，右；
```

但当前作用域没有可见的“加”。

优先检查：

```text
名字是否拼错？
完整道路是什么？
是否需要显式引路？
项目常路是否正确？
是不是旧名字已经弃用？
当前版本是否仍提供该字？
```

---

# 第四章　“找不到”不等于“字不存在”

可能存在：

```text
正式字已经在字库
```

但：

```text
当前源码没有可见入口
```

因此必须区分：

```text
不存在
和
不可见
```

一个高质量诊断应明确：

```text
REGISTERED_BUT_NOT_VISIBLE
```

而不是笼统：

```text
unknown symbol
```

---

# 第五章　第二类：没形成

典型情况：

```text
@ 名字已经写了
但正文没有通过
```

可能原因：

```text
输入不完整
输出不完整
失败未处理
效果不明确
公开能力不稳定
关系没有闭合
```

重要原则：

# **名字声明不等于 FormalZi 已经形成。**

形成失败时：

```text
不能污染正式字库
不能留下半个FormalZi
不能产生不完整Nature
```

---

# 第六章　名字形成失败时应该看什么

诊断应至少显示：

```text
NameClaim：
求和

形成阶段：
ValidatedZiText → FormalZiCommit

失败原因：
返回结果未覆盖全部路径

影响：
未生成FormalZi
未写入SemanticRegistry
```

这样使用者知道：

```text
失败发生在“形成”
而不是“调用”
```

---

# 第七章　第三类：吃不下

这是最典型的字号关系错误。

可能是：

```text
类型不匹配
角色不匹配
必需端口缺失
输出数量不匹配
所有权不匹配
Generation不匹配
```

例如：

```hanrain
结果* 加 "3"，4；
```

如果当前“加”只接受整数：

```text
"3"
文本
```

不能直接进入：

```text
整数端口
```

---

# 第八章　“类型相同”仍然可能吃不下

假设右字吐：

```text
正文：文本
来源：文本
```

左字吃：

```text
输入：文本
标签：文本
```

类型都是：

```text
文本
```

仍不能自动判断：

```text
正文 → 输入？
正文 → 标签？
来源 → 输入？
来源 → 标签？
```

如果存在多个合法映射：

```text
必须报歧义
```

而不是：

```text
按位置猜
```

---

# 第九章　第四类：无权发生

最容易被误解。

可能出现：

```text
字能找到
类型也对
端口也对
```

但仍然拒绝。

原因可能是：

```text
当前关系没有许可
Guan拒绝
Provider不满足
安全要求不允许
效果不允许
Generation陈旧
```

所以：

# **长期能做，不等于本场允许做。**

---

# 第十章　长期能力与本场许可

可以简化成：

```text
Nature
回答：
这个字原则上能做什么

Mandate
回答：
这场关系实际允许它做什么
```

因此必须满足：

```text
Mandate
⊆
Nature
```

本场许可不能扩大长期能力。

---

# 第十一章　第五类：结果没人接

例如某个文字吐：

```text
成功结果
失败结果
状态
```

而当前关系只消费：

```text
成功结果
```

剩余：

```text
失败
状态
```

不能静默消失。

常见诊断：

```text
UNCONSUMED_HAO
UNHANDLED_FAILURE
UNRESOLVED_OUTPUT
```

---

# 第十二章　未消费号不一定都是错误

某些输出可以明确声明：

```text
允许忽略
```

或者：

```text
已经被证明无用
```

但必须有正式依据。

不能：

```text
编译器觉得没用
→ 自动扔掉
```

---

# 第十三章　第六类：生命周期不允许

典型情况：

```text
MOVE后继续使用
借用未释放
重复释放
旧Generation访问
Pending未结束就关闭
仍有Obligation就回收
```

这类错误通常不是：

```text
类型错
```

而是：

```text
关系状态不再允许当前动作
```

---

# 第二编　怎样读一条高质量汉雨诊断

# 第十四章　诊断至少回答六个问题

每条高级诊断最好能够回答：

```text
1. 哪个名字？
2. 哪条道路？
3. 哪个正式字？
4. 哪个号或端口？
5. 哪条关系失败？
6. 用户下一步应该怎么修？
```

---

# 第十五章　推荐诊断结构

例如：

```text
错误：
HaoBinding无法唯一成立

文字：
标准——文本——拼接

当前关系：
格式化输出

候选号：
正文：文本
标签：文本

目标端口：
左：文本
右：文本

原因：
存在两个同等合法绑定

建议：
显式命名中间号
或
显式指定端口角色
```

比：

```text
type mismatch
```

更有用。

---

# 第十六章　道路错误应显示相近候选

例如：

```text
找不到：
标准——整数——求和
```

如果当前注册表有：

```text
标准——整数——加
```

并且旧名：

```text
求和
```

已经成为兼容别名，诊断应明确：

```text
旧名可迁移到：
标准——整数——加
```

---

# 第十七章　Formation 错误必须说明“没有污染”

如果 FormalZi 形成失败，诊断应明确：

```text
未提交FormalZi
未修改SemanticRegistry
未占用正式道路
```

这样使用者可以放心继续修正文档。

---

# 第十八章　关系拒绝应显示权威来源

如果当前关系被拒绝：

```text
Nature允许
但Mandate未授予
```

应明确写：

```text
长期能力：
允许文件写入

本场许可：
仅允许读取

拒绝原因：
本场Mandate不包含write effect
```

---

# 第十九章　Generation 错误要显示新旧世代

例如：

```text
STALE_GENERATION

引用：
Generation 7

当前实例：
Generation 8

状态：
旧实例已停止接收新关系

建议：
重新取得当前名字绑定
或
执行正式迁移
```

---

# 第二十章　生命周期错误要显示未决义务

例如：

```text
CLOSE_REJECTED

资源：
文件句柄 #42

原因：
仍有1个BORROW
仍有1个Pending读取

建议：
结束借用并等待Pending完成后再闭
```

这比：

```text
resource busy
```

更符合汉雨。

---

# 第三编　调试方法

# 第二十一章　第一法：展开连字

遇到：

```hanrain
*说 格式化 校验 解析 读取 路径；
```

先改成：

```hanrain
原文* 读取 路径；
结构* 解析 原文；
结果* 校验 结构；
文本* 格式化 结果；
*说 文本；
```

这样可以逐边检查：

```text
读取 → 原文
原文 → 解析
解析 → 结构
...
```

---

# 第二十二章　第二法：给隐藏号命名

如果：

```text
编译器说中间绑定歧义
```

不要继续猜。

直接把：

```text
隐藏号
```

写出来。

显式号名是关系调试最有效的方法之一。

---

# 第二十三章　第三法：查看完整道路

短名：

```text
加
```

可能有多个候选。

调试时优先查看：

```text
完整语义道路
```

而不是：

```text
当前文件里哪个先出现
```

---

# 第二十四章　第四法：查看公开能力

检查：

```text
输入端口
输出端口
效果
失败
所有权
生命周期
Provider
```

不要只看名字。

---

# 第二十五章　第五法：看本场关系

如果字本身没有问题：

```text
检查RelationNeed
检查Guan
检查Mandate
检查Generation
```

问题可能不在文字本身，而在：

```text
当前这一次关系
```

---

# 第二十六章　第六法：最后才看 MIR

只有当：

```text
源码关系已经确认正确
```

但机器行为仍然错误时，才逐步查看：

```text
CFG
SSA
HanRain MIR
C11
LLVM
Native
```

不要一开始就从汇编猜高层关系错误。

---

# 第四编　高级关系权威链

# 第二十七章　从用户源码到正式关系

可以把当前主链简化成：

```text
源码名字与道路
↓
FormalZi
↓
Nature
↓
RelationNeed
↓
Guan
↓
Mandate
↓
HaoBinding
↓
Prepared
↓
RainCommit
↓
RelationHan
↓
CFG / SSA
↓
唯一 HanRain MIR
↓
C11 / LLVM / Native
```

其中：

```text
Dao
```

属于编译器内部隐藏合法空间。

---

# 第二十八章　“道”不属于用户可见字库

这是重要冻结边界：

# **道是编译器内部隐藏关键字 / 根语义上下文。**

因此普通用户源码、字库条目、号库 Schema、公共 API 中都不应：

```text
声明道
引道
继承道
扩展道
把道当FormalZi
```

用户看到的应该是：

```text
具体诊断
具体关系
具体合法性事实
```

而不是必须操作“道对象”。

---

# 第二十九章　FormalZi：正式文字是谁

FormalZi 回答：

```text
这个成熟文字到底是谁？
```

它代表稳定的正式文字身份。

一个 FormalZi 可以有：

```text
规范名
别名
道路
Nature
版本
实现候选
```

但：

```text
名字
不等于
FormalZi
```

---

# 第三十章　为什么名字改了，FormalZi 可以不变

如果：

```text
求和
```

改规范名为：

```text
加
```

但语义和正式身份没有变化：

```text
FormalZi仍可保持同一稳定身份
```

旧名字可以成为：

```text
兼容别名
```

---

# 第三十一章　Nature：长期能力

Nature 属于 FormalZi。

它描述：

```text
输入
输出
效果
失败
资源
所有权
长期约束
```

它不属于某一次调用。

可以记成：

# **Nature 是“这个字长期是什么”。**

---

# 第三十二章　术码：Nature 的摘要

术码可以从 Nature 派生。

用途：

```text
索引
筛选
候选分桶
缓存
```

但：

```text
术码
不能替代Nature
```

所以：

# **术码快找，Nature定真。**

---

# 第三十三章　RelationNeed：本场到底要完成什么

RelationNeed 不是 FormalZi 的属性。

它属于：

```text
当前这场关系
```

例如：

```text
把用户输入解析为0—100之间的整数
```

RelationNeed 可以包括：

```text
目标
输入
输出
安全要求
性能要求
资源约束
```

---

# 第三十四章　姓：立问与治理根

在关系形成中，“姓”负责：

```text
立当前核心需求
确定治理根
组织候选能力域
```

不能把姓理解成：

```text
万能调度器
```

它更多回答：

```text
这场关系从哪里立问？
```

---

# 第三十五章　氏：候选能力与现实实现域

氏负责展开：

```text
Provider
资源
实现环境
候选能力域
```

它不直接拥有执行权。

可以记成：

```text
姓立其问
氏开其域
```

---

# 第三十六章　名：正式入口

名负责：

```text
把“可能方法”
变成
“当前正式采用的入口”
```

所以：

```text
名
不是可以省略的装饰
```

---

# 第三十七章　Guan：本场合法空间

Guan 负责：

```text
谁能进入
哪些端口可用
哪些效果允许
哪些资源允许
```

它是：

```text
关系边界
```

而不是：

```text
关系本体
```

---

# 第三十八章　Mandate：本场许可

可以简化：

```text
Mandate
=
RelationNeed
∩
GuanAllowance
∩
MingProjection(Nature)
∩
ShiGrant
```

普通用户无需手写这个公式。

但要理解：

# **Mandate 是长期能力在当前关系中的合法缩影。**

---

# 第三十九章　Mandate 不能做什么

Mandate 不能：

```text
创造FormalZi
扩大Nature
绕过Guan
忽略所有权
忽略Generation
```

---

# 第四十章　HaoBinding：具体号绑定具体端口

HaoBinding 只回答：

```text
哪个具体号
→
哪个具体端口
```

它不能：

```text
选择FormalZi
创造Mandate
扩大权限
```

这是非常关键的权威分离。

---

# 第四十一章　为什么绑定要在正式关系前完成

如果：

```text
具体号还不知道进哪个端口
```

就已经执行：

```text
外部效果
```

后面发生歧义时就难以回滚。

因此需要：

```text
先形成唯一绑定
再进入准备
```

---

# 第五编　三刀流

# 第四十二章　三刀流解决什么问题

复杂关系常遇到三类问题：

```text
材料是否合格？
方法哪个好？
当前模型够不够？
```

三刀流把它们分成：

```text
乱刀
利刀
道刀
```

---

# 第四十三章　乱刀：处理具体材料

乱刀重点检查：

```text
号
端口
类型
所有权
生命周期
Generation
局部事实
```

它回答：

> 当前手里的材料能不能参与？

例如：

```text
这个号类型对吗？
这个BORROW还有效吗？
这个Generation过期了吗？
```

---

# 第四十四章　利刀：选择方法

利刀处理：

```text
多个Provider
多个合法实现
多个可行方法
```

它回答：

> 在当前合法候选中，哪个方法更合适？

可以参考：

```text
性能
资源
稳定性
成本
```

但：

```text
只能在合法候选中择优
```

---

# 第四十五章　道刀：判断模型是否够用

道刀回答：

```text
当前关系能闭合吗？
需要换法吗？
需要升模吗？
应该拒绝吗？
已经无解吗？
证据是否陈旧？
```

它不是：

```text
运行时万能控制器
```

而是：

```text
关系充分性审议
```

---

# 第四十六章　三刀流不能获得新的语义权威

三刀流可以产生：

```text
证据
建议
候选排序
闭合判断
```

但不能：

```text
创建第二套IR
直接修改FormalZi
绕过Mandate
自行提交关系
```

---

# 第四十七章　乱、利、道的简单例子

矩阵运算：

```text
乱刀：
输入维度对吗？
缓冲有效吗？

利刀：
CPU / GPU / NPU
哪个合法且更优？

道刀：
当前模型是否足以满足精度与资源要求？
如果都不满足，应拒绝还是升模？
```

---

# 第六编　二人转

# 第四十八章　二人转解决什么问题

二人转主要解决：

```text
多个有限候选
如何形成
如何竞争
如何准备
如何避免准备阶段污染正式状态
```

它可以理解成：

# **有限候选的关系准备协议。**

---

# 第四十九章　主关系与次关系

可以简化：

```text
主关系
负责正式目标

次关系
负责提出候选方案
```

次关系不能直接把：

```text
候选
```

变成：

```text
正式事实
```

---

# 第五十章　双锚窗口

二人转可以在：

```text
当前正式锚
和
候选新锚
```

之间形成有限准备空间。

目标：

```text
旧状态仍然可用
新状态可以准备
```

但新状态尚未正式发布。

# 第五十一章　Prepared 屏障

Prepared 表示：

```text
候选已经准备完成
```

但：

# **Prepared 不等于已经发生。**

Prepared 之后仍需要：

```text
正式提交
```

---

# 第五十二章　二人转不拥有 RainCommit

重要边界：

```text

只负责候选构造、竞争、准备

雨
负责正式提交
```

所以：

# **二人转备其变，雨使其变真正发生。**

# 第七编　雨

# 第五十三章　雨是什么

雨的用户级定义：

> 在关允许、中完成绑定、汉态允许后，沿系真正发生的一次有类型关系事件。

简化：

```text
合法
+
绑定完成
+
准备完成
↓
真正发生
```

---

# 第五十四章　为什么雨必须唯一

如果同一场关系存在：

```text
两个同时拥有正式提交权的机制
```

会产生：

```text
双重事实
状态分裂
难以回滚
```

所以需要：

```text
唯一正式提交点
```

---

# 第五十五章　RainCommit 的意义

RainCommit 之前：

```text
都只是准备、证据、候选
```

RainCommit 之后：

```text
关系事实正式改变
```

例如：

```text

资源所有权真的转移
```

# 第八编　汉

# 第五十六章　汉是什么

汉不是：

```text
整个运行时状态
程序计数器
所有变量集合
```

汉是：

> 一场公共关系继续、闭合和回收所需的最小一致态。

---

# 第五十七章　汉通常关心什么

例如：

```text

Obligation
Generation
活动前沿
未释放资源
未消费输出
```

它只保存：

```text
关系是否还能继续
关系能不能关闭
资源能不能回收
```

所需事实。

---

# 第五十八章　为什么汉必须最小

如果 Han 保存整个运行时：

```text
所有局部变量
所有SSA
所有对象
所有缓存
```

会变成：

```text
第二套Runtime State
```

这违背：

```text
唯一执行语义
```

原则。

---

# 第五十九章　汉与 CFG/SSA 的边界

Han 不替代：

```text

SSA
```

CFG 负责：

```text
控制顺序
```

SSA 负责：

```text
值依赖
```

Han 只保留：

```text
关系继续/闭合/回收所需的公共一致事实
```

# 第十四编　测试与证据

# 第八十五章　每个错误都应该有反例测试


必须有：

```text

```

而不是只测：

```text

```

# 第八十六章　关系前证

汉雨特别适合：

```text

```

从而：

```text
提前截断错误设计
减少无意义重型测试
```

这不是替代所有测试，而是：

```text
把明显不合法关系尽早拒绝
```

# 第八十七章　测试不能把外层超时直接判定为回归

完整仓库测试可能非常长。

外层 timeout 只能说明：

```text
TEST_HARNESS_TIMEOUT
或
NOT_COMPLETED
```

不能直接说明：

```text
HANRAIN_REGRESSION
```

只有：

```text
明确FAILED
断言
后端差分
死锁
资源异常
```

等证据，才能归责为真实回归。

---

# 第八十八章　为什么这也属于关系诊断

因为：

```text
测试Harness
```

和：

```text
被测关系
```

是两个不同边界。

Harness 超时：

```text
不能自动证明
被测语义失败
```

这正是权威分离原则。

# 结束语

汉雨最有价值的错误信息，不是：

```text
“第42行失败”
```

而是：

```text
当前是哪一场关系？
它已经知道什么？
还缺什么？
谁没有权力？
哪个号不能进入哪个端口？
哪个世代已经失效？
哪些义务还没完成？
为什么此刻不能继续？
```

只有把这些问题说明白：

```text
错误
才从“程序坏了”
变成
“关系为什么无权继续”的可解释证据。
```

最终总句：

# **错必有因，因必有据；名定其身，性定其能，命限其用，号入其中；三刀审之，二人转备之，雨使其成，汉守其续，能证则消，终归于机。**

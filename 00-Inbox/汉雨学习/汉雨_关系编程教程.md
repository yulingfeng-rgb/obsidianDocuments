# 汉雨 HanRain《关系编程教程》

## ——先问关系为何成立，再问字怎样执行；字自治其内，号通其间，关系有据而成

**文档性质：** 用户进阶教程  
**适用阶段：** 已完成《源码语言教程》或具备基本汉雨源码阅读能力  
**主要读者：** 希望真正按照“面向关系”方式设计汉雨程序的开发者  
**本文目标：** 从“会写字句”推进到“会设计关系”，能够正确处理多字协作、号绑定、失败、资源、所有权、生命周期、并发和动态关系  
**本文不要求：** 直接实现三刀流、二人转、RelationHan、RainCommit 或编译器内部 IR

> 本教程关注“怎样思考程序”。  
> 语法细节以《源码语言教程》为准；字库条目和正式能力查询以《字库使用手册》《标准字库参考》为准。

# 第一章　什么叫“关系编程”

传统编程经常先问：

```text
有哪些对象？
有哪些函数？
哪个函数调用哪个函数？
哪个对象拥有哪个对象？
```

汉雨更希望先问：

```text
当前要完成什么关系？
谁参与？
各自能做什么？
什么号需要在它们之间流动？
什么条件下这场关系才合法？
关系什么时候真正发生？
什么时候可以结束？
```

因此：

# **关系编程，不是把“关系”做成一个新对象，而是把关系作为组织程序的第一视角。**

---

# 第二章　关系不是“对象之间的一条线”

不要把汉雨的关系只理解成：

```text
A —— B
```

一场完整关系至少要回答：

```text
为什么发生？
谁参与？
交换什么？
谁可以吃什么？
怎样传导？
什么情况下拒绝？
发生之后还剩什么义务？
什么时候可以关闭？
```

所以更准确地说：

```text
关系
=
目标
+
参与者
+
字号传递
+
边界
+
本场许可
+
变化
+
生命周期
```

---

# 第三章　关系是优先语义单位

汉雨当前最重要的设计之一是：

# **关系是优先语义单位。**

这不代表：

```text
运行时必须 new RelationObject()
```

而是说：

```text
字
号
资源
失败
所有权
状态变化
```

都应该能够说明：

> 它们属于哪一场关系，以及在这场关系中承担什么职责。

---

# 第四章　一个最小关系

例如：

```hanrain
和* 加 3，4；
```

表面只有：

```text
3
4
加
和
```

关系可以拆成：

```text
目标：
得到3和4的和

参与文字：
加

输入号：
3、4

输出号：
和
```

最小图：

```text
3 ─┐
   ├→ 加 → 和
4 ─┘
```

这已经是一场关系。

---

# 第五章　字是自治计算主体

关系优先，不意味着字失去自治。

一个成熟字仍然拥有自己的：

```text
输入
输出
私有状态
转换规则
失败
效果
```

可以把字粗略理解成：

```text
Zi = <状态, 输入, 输出, 转换, 效果>
```

但关系不应该随意读取字的全部内部状态。

原则：

# **字内自治，字际公开。**

字内部怎样实现：

```text
循环
缓存
局部状态
临时值
算法
```

通常属于该字自己。

跨越字边界时，才进入公共关系。

---

# 第六章　号是公共关系的主要载荷

字号之间真正流动的是“号”。

号可以承载：

```text
值
文本
数组
引用
文件句柄
资源
能力
错误
结果
Generation
证明摘要
```

因此：

```text
号
≠ 普通变量值
```

一个号还可能带有关系属性：

```text
谁产生
谁拥有
是否可以复制
作用域
生命周期
世代
可以进入哪些端口
```

---

# 第七章　公共关系必须能够还原成字号关系

即使源码写成连字：

```hanrain
*说 格式化 加 3，4；
```

内部仍应该能够还原为：

```text
3、4
↓
加
↓ h0
格式化
↓ h1
说
```

也就是：

```text
字 → 号 → 字
```

而不是长期只保存：

```text
字 → 字
```

这保证：

```text
类型
所有权
生命周期
失败
端口
```

都有明确落点。

---

# 第八章　先有“需求”，再有参与者

关系设计的第一步不是：

```text
我有字A、字B、字C，怎么串起来？
```

而是：

```text
当前到底要完成什么？
```

例如：

```text
把用户输入解析成整数，
验证范围，
成功后写入配置，
失败时返回诊断。
```

这可以先写成一个关系需求：

```text
RelationNeed：
输入：
    用户文本

目标：
    得到合法配置整数

要求：
    范围合法
    失败必须可解释
    写入成功后才算完成
```

然后再寻找参与文字。

---

# 第九章　从“找函数”改成“找关系能力”

传统思维：

```text
我需要 parseInt()
```

关系思维：

```text
我需要：
文本
→ 某个能够解析整数的成熟字
→ 整数或格式错误
```

然后查字库：

```text
输入：文本
输出：整数
失败：格式错误
效果：纯
```

找到正式文字：

```text
解析整数
```

这样更适合汉雨的持久字库。

---

# 第十章　长期能力：这个字原则上能做什么

成熟文字有长期公开能力。

例如“校验”长期可能支持：

```text
输入：
正文：文本

可选输入：
来源
警告

输出：
校验结果

效果：
只读

失败：
格式错误
证明过期
```

这类长期能力在内部由 Nature 等正式事实表示。

普通用户只需要理解：

# **长期能力回答“这个字原则上能做什么”。**

---

# 第十一章　本场许可：这次关系实际让它做什么

长期能力不是本次调用的无限授权。

例如“校验”原则上能接受：

```text
正文
正文+来源
正文+警告
正文+来源+警告
```

但当前关系可能只需要：

```text
正文+来源
```

本场许可回答：

```text
这次实际启用哪些输入？
允许哪些效果？
选哪个Provider？
允许怎样失败？
```

内部可能由 Mandate （命契）等机制表达。

用户应形成：

# **性定其能，命限其用。**

也就是：

```text
长期能力
≠
本次全部都能用
```

---

# 第十二章　本场许可不能扩大长期能力

如果一个字长期只有：

```text
读取文本
```

当前关系不能因为“方便”就临时宣布：

```text
它也能修改文件
```

所以：

```text
本场许可
⊆
长期能力
```

这是非常重要的安全边界。

---

# 第十三章　“能找到”不等于“能使用”

字库里存在：

```text
删除文件
```

只说明：

```text
这个成熟文字存在
```

当前关系还要回答：

```text
当前环境允许吗？
有文件系统Provider吗？
当前身份有权限吗？
输入句柄有效吗？
Generation正确吗？
所有权允许吗？
```

因此：

# **存在性、能力和本场许可是三件不同的事。**

---

# 第十四章　关：关系的合法边界

“关”可以先用用户视角理解成：

> 当前关系的门槛和边界。

它可以限制：

```text
哪些参与者能进入
哪些端口可用
哪些能力被允许
哪些资源能访问
哪些效果禁止
```

关不是：

```text
万能调度器
中央运行时
```

它只负责：

```text
什么可以进入当前关系
```

---

# 第十五章　中：当前关系中的唯一对应

当一个字吐多个号，而另一个字也有多个端口时，需要确定：

```text
哪个号
→
哪个端口
```

“中”可以理解成：

> 当前关系里已经成立的唯一对应和闭合点。

例如：

```text
右字吐：
正文
来源
错误

左字吃：
正文
来源
```

合法绑定必须明确：

```text
右.正文 → 左.正文
右.来源 → 左.来源
```

而不是靠位置猜。

---

# 第十六章　系：关系怎样继续传导

“系”可以理解成：

> 值、控制和效果如何沿着关系继续向前。

例如：

```text
读取
↓ 数据
解析
↓ 结构
校验
↓ 结果
提交
```

这是数据系。

而：

```text
解析失败
↓
诊断
```

是失败传导。

条件分支、循环、异步等待也属于更广义的传导结构。

---

# 第十七章　号绑定：关系真正细化到端口

假设右字：

```text
拆开
```

吐出：

```text
头
尾
```

左字：

```text
拼回
```

需要：

```text
头
尾
```

关系绑定是：

```text
拆开.头 → 拼回.头
拆开.尾 → 拼回.尾
```

内部可形成 HaoBinding 等证明。

用户层最重要的理解：

# **关系不是“两个字能不能连”，而是“具体哪些号能不能进入具体哪些端口”。**

---

# 第十八章　绑定必须唯一

如果：

```text
右字吐两个文本
左字也有两个文本输入
```

而语义角色不清楚：

```text
文本A
文本B

→

左输入1
左输入2
```

仅凭类型可能有两个合法排列。

此时编译器不应该：

```text
按出现顺序猜
```

而应该：

```text
报歧义
```

用户可以：

```text
显式给号命名
显式选择端口
缩小关系
```

---

# 第十九章　类型兼容只是第一步

绑定是否成立还要检查：

```text
类型
角色
所有权
生命周期
Generation
效果顺序
失败出口
Provider
本场许可
```

因此：

```text
类型相同
≠
关系一定成立
```

这是关系编程和普通函数签名匹配的重要差异。

---

# 第二十章　连字的本质

连字：

```hanrain
*说 格式化 加 3，4；
```

不是简单函数复合。

它更准确地表示：

```text
右字先吐号
↓
左字依据长期能力和本场许可
选择合法号绑定
↓
左字继续执行
```

因此：

# **连字是有限关系转位。**

---

# 第二十一章　多号连字

例如：

```text
拆开
吐：
头
尾

拼回
吃：
头
尾
```

表面可以形成连字。

但内部必须保留：

```text
头号
尾号
```

不能因为源码省略名字，就认为：

```text
拆开直接成为拼回的一部分
```

---

# 第二十二章　未消费号必须有去向

右字吐：

```text
正文
错误
状态
```

左字只吃：

```text
正文
```

那么：

```text
错误
状态
```

不能凭空消失。

必须明确：

```text
由谁消费？
是否允许丢弃？
是否进入日志？
是否进入失败路？
是否被证明无用？
```

所以：

# **关系不只关心“用了什么”，还关心“剩下什么”。**

---

# 第二十三章　Result 是一场分叉关系

例如：

```text
解析整数
```

可能吐：

```text
成功整数
或
格式错误
```

这不是“正常值+异常机制”两套世界。

可以统一理解为：

```text
一次关系
↓
两个合法结果方向
```

用户必须对两个方向负责。

---

# 第二十四章　Option 是“存在关系”与“不存在关系”

查找：

```text
查找元素
```

可能得到：

```text
有值
无值
```

不要擅自把：

```text
无值
```

等同：

```text
0
false
""
```

因为这些都是具体号，不是“无结果”关系。

---

# 第二十五章　失败本身也是号和关系

一个失败可以携带：

```text
错误码
诊断
来源
失败位置
恢复建议
```

所以失败不是：

```text
程序之外的噪声
```

它也是关系的一部分。

---

# 第二十六章　局部失败和公共失败

字内部可能发生：

```text
一次缓存未命中
一次内部重试
一个临时候选失败
```

如果字自己处理完毕：

```text
不必成为公共关系失败
```

只有影响：

```text
公开输出
资源
HaoBinding
生命周期
Generation
关系闭合
```

时，才需要上升为公共失败。

---

# 第二十七章　资源是一种关系参与事实

文件、网络连接、GPU缓冲、设备句柄都不能只当普通整数号。

资源关系还需要：

```text
谁持有
谁借用
谁可以修改
什么时候释放
当前世代
当前Provider
```

例如：

```hanrain
文件* 打开 路径；
数据* 读取 文件；
*关闭 文件；
```

背后是一条资源生命周期关系。

---

# 第二十八章　COPY、MOVE、BORROW

## COPY

```text
A拥有号
↓ COPY
A继续可用
B也得到可用副本
```

## MOVE

```text
A拥有号
↓ MOVE
B成为新持有者
A不得继续使用旧号
```

## BORROW

```text
A拥有资源
↓ BORROW
B临时使用
↓
借用结束
A继续拥有
```

这些不是语法花样，而是：

```text
关系是否合法
```

的一部分。

---

# 第二十九章　为什么 MOVE 后继续使用必须拒绝

例如：

```text
资源从甲移动到乙
```

如果甲仍继续使用：

```text
同一资源出现两个互相冲突的持有关系
```

所以拒绝不是“保守检查”，而是保持关系一致性。

---

# 第三十章　生命周期不是“对象活多久”

在汉雨里更适合问：

```text
这场关系还有什么未完成？
```

例如文件关系：

```text
打开
↓
读取进行中
↓
还有异步Pending
↓
还不能关闭
```

生命周期取决于：

```text
Pending
Obligation
借用
未消费输出
资源释放
```

而不仅是：

```text
变量是否还在作用域
```

---

# 第三十一章　汉：关系继续、闭合和回收的最小事实

用户层可以把“汉”理解成：

> 当前这场关系还活着吗？为什么还不能结束？

它不应该保存整个程序。

只需要足以判断：

```text
继续
等待
关闭
回收
```

的最小公共事实。

例如：

```text
还有一个异步请求未完成
还有一个借用未归还
还有一个输出未消费
```

都可能使关系暂时不能结束。

---

# 第三十二章　雨：准备好的变化真正发生

用户可以把“雨”理解成：

> 一次已经合法准备好的关系变化，真正成为事实的提交点。

例如：

```text
候选文件写入
```

在提交前可能只是：

```text
准备好
检查通过
```

真正提交后：

```text
文件内容改变
```

所以：

# **准备不等于发生。**

---

# 第三十三章　为什么“准备”和“提交”必须分开

假设：

```text
余额转账
```

先准备：

```text
账户存在
权限正确
余额足够
目标账户有效
```

如果准备阶段就修改余额：

```text
后续检查失败
→ 状态已经部分改变
```

所以需要：

```text
先准备
↓
全部成立
↓
再提交
```

这是很多复杂关系保持原子性的基础。

---

# 第三十四章　一场关系的用户级生命周期

可以简化为：

```text
未形成
↓
目标形成
↓
参与者确定
↓
字号绑定
↓
准备完成
↓
正式发生
↓
运行 / 等待
↓
可以关闭
↓
可以回收
↓
结束
```

高级机制里会有更精确的状态名。

普通用户只需要记住：

# **关系不是“调用一下就结束”，可能有形成、发生、等待和回收阶段。**

---

# 第三十五章　Generation：同一个名字，不一定还是同一个实例

动态服务：

```text
问候
```

可能当前指向：

```text
Generation 7
```

热更新后指向：

```text
Generation 8
```

名字可以保持：

```text
问候
```

但旧引用不能自动假装自己已经属于新实例。

因此：

```text
稳定名字
≠
当前具体实例
```

---

# 第三十六章　为什么 Generation 很重要

如果：

```text
旧号来自Generation 7
```

却访问：

```text
Generation 8
```

可能出现：

```text
旧资源误连
旧插件调用新ABI
已释放槽位被重新解释
```

所以世代检查是动态关系安全的重要组成部分。

---

# 第三十七章　Provider：同一个能力可以有多个现实实现

一个正式字可能表达：

```text
矩阵乘
```

现实环境可以提供：

```text
CPU实现
GPU实现
NPU实现
```

长期语义相同或兼容，但 Provider 不同。

关系设计应分开：

```text
我要什么能力
和
当前由谁实现
```

---

# 第三十八章　为什么 Provider 不应该决定语义

如果 GPU Provider 突然不存在：

```text
不应该改变“矩阵乘”是什么
```

只是：

```text
当前实现候选变化
```

因此：

```text
FormalZi / 长期能力
和
Provider
```

必须分离。

---

# 第三十九章　安全也是关系需求

不同关系可以需要不同安全形状。

例如：

```text
图片像素转换
```

可能只需要：

```text
内存安全
单线程
无事务
```

数据库转账可能需要：

```text
强一致
原子提交
严格世代
持久恢复
审计
```

所以：

# **安全不是一个全局0—5等级，而可以成为每场关系的多维需求。**

---

# 第四十章　但基础安全底线不能关闭

不能因为追求性能就允许：

```text
MOVE后继续使用
伪造正式身份
绕过类型
扩大本场许可
忽略Generation
```

这些属于语言基础安全。

关系可选择的是：

```text
锁策略
事务强度
审计
恢复
复制隔离
同步方式
```

等额外策略。

---

# 第四十一章　性能只能在合法候选中择优

假设三个方案：

```text
A Mutex 100ns
B 关系锁 160ns
C 复制隔离 800ns
```

先做：

```text
安全要求
∩ 长期能力
∩ 本场许可
∩ 平台能力
```

得到合法候选。

然后：

```text
在合法候选中选成本最低
```

不能：

```text
最快
→ 即使不合法也选
```

---

# 第四十二章　对象在关系编程中的位置

汉雨不是说：

```text
对象不存在
```

而是：

```text
对象不再是最高组织本体
```

一个对象可以理解为：

```text
当前关系中具有稳定身份、状态和边界的参与者投影
```

例如：

```text
文件
账户
设备
用户
```

仍然有意义。

---

# 第四十三章　过程在关系编程中的位置

过程也不是被删除。

过程回答：

```text
关系怎样推进
```

例如：

```text
读取
解析
校验
提交
```

它是关系传播和方法计划的一种观察。

所以：

```text
对象
过程
```

都可以存在。

但要问：

```text
它们在当前关系里承担什么？
```

---

# 第四十四章　从 OOP 迁移：先不要画类图

假设要做订单处理。

传统做法可能先画：

```text
Order
Customer
PaymentService
InventoryService
OrderManager
```

关系做法先画：

```text
订单请求
↓
校验库存
↓
锁定库存
↓
支付
↓
确认
↓
失败回滚
```

再确定：

```text
哪些成熟字参与
哪些号流动
哪些资源必须保持一致
```

对象仍然可以参与，但不主宰全部设计。

---

# 第四十五章　从函数式思维迁移：不要只看输入输出类型

函数式开发者可能认为：

```text
A -> B
B -> C
所以可以复合
```

汉雨还要问：

```text
B是谁拥有？
有没有失败出口？
有外部效果吗？
Generation一致吗？
Provider合法吗？
```

所以类型兼容只是关系成立的一部分。

---

# 第四十六章　从流程编排迁移：流程不是关系全部

工作流：

```text
A
↓
B
↓
C
```

只表达执行顺序。

关系还要表达：

```text
字号绑定
权限
所有权
失败
生命周期
资源
```

因此：

```text
关系图
≠ 纯流程图
```

---

# 第四十七章　典型模式一：解析—校验—提交

需求：

```text
读取用户配置
解析
校验
合法后提交
```

关系：

```text
文本
↓
解析
├─ 失败 → 诊断
└─ 成功结构
       ↓
     校验
     ├─ 失败 → 诊断
     └─ 合法配置
             ↓
           提交
```

关键：

```text
提交前不改变正式状态
```

---

# 第四十八章　典型模式二：请求—响应

```text
请求号
↓
服务字
↓
响应号
```

如果异步：

```text
请求
↓
Pending
↓
等待
↓
响应
```

关系在等待期间仍然存在。

不能因为函数返回了“future句柄”就认为业务关系已经结束。

---

# 第四十九章　典型模式三：生产者—消费者

```text
生产字
↓ 数据号
消费者字
```

需要考虑：

```text
缓冲容量
所有权
背压
消费者失败
生产者是否继续
```

所以它不只是：

```text
队列.put()
队列.get()
```

而是一场带资源和生命周期的关系。

---

# 第五十章　典型模式四：资源获取—使用—释放

```text
获取
↓ 资源号
使用
↓
释放
```

需要保证：

```text
释放不能早于使用完成
失败时也要释放
借用结束后才能回收
```

这类模式非常适合关系化描述。

---

# 第五十一章　典型模式五：多Provider择一

需求：

```text
执行矩阵运算
```

候选：

```text
CPU
GPU
NPU
```

关系先限定：

```text
语义要求
精度
资源
延迟预算
```

然后选择合法实现。

Provider的选择不能改变：

```text
矩阵运算本身的正式语义
```

---

# 第五十二章　典型模式六：热更新

公开名字：

```text
问候
```

当前：

```text
Generation 7
```

后台准备：

```text
Generation 8
```

流程：

```text
旧实例继续服务
新实例并行准备
↓
新实例验证
↓
原子发布
↓
旧实例停止接新请求
↓
等待旧Pending结束
↓
回收
```

可以理解为：

# **名字稳定，实例轮换；准备并行，发布串行。**

---

# 第五十三章　典型模式七：事务型关系

例如：

```text
账户A
↓ 转账
账户B
```

要求：

```text
余额检查
权限
原子提交
失败回滚
审计
```

这种关系特别强调：

```text
准备
≠
提交
```

---

# 第五十四章　关系设计的第一张图：目标图

不要先画机器执行。

先写：

```text
关系目标
输入
成功输出
失败输出
外部效果
资源
```

例如：

```text
目标：
导入配置

输入：
配置文件路径

成功：
已提交配置

失败：
读取错误 / 解析错误 / 校验错误

效果：
读取文件
更新配置存储
```

---

# 第五十五章　第二张图：字号图

然后画：

```text
路径号
↓
读取
↓ 文本号
解析
↓ 配置候选号
校验
↓ 合法配置号
提交
```

失败边也画出来。

---

# 第五十六章　第三张图：资源和生命周期图

例如：

```text
文件句柄
谁拥有？

配置事务
何时创建？

提交失败
谁回收？
```

将这些补上，关系设计才完整。

---

# 第五十七章　控制图不能被字号图替代

字号图告诉：

```text
什么流向什么
```

控制图还要告诉：

```text
哪个分支执行
哪个循环回去
什么时候等待
什么时候退出
```

所以：

```text
Public Zi-Hao Graph
和
ControlRegion / CFG
```

职责不同。

---

# 第五十八章　值依赖也不能只靠公共字号图

编译器最终还需要：

```text
SSA
```

表达精确值依赖。

因此用户层关系图是：

```text
高层公共语义
```

最终会下降成：

```text
控制
值
调用
机器操作
```

---

# 第五十九章　关系编程不是关系运行时

这是非常重要的性能边界。

静态关系如果已经完全确定：

```text
字是谁
号绑定谁
分支怎么走
Provider是谁
```

最终可以直接成为：

```text
函数调用
SSA值
机器指令
跳转
```

不需要运行时长期保留：

```text
Mandate对象
三刀流对象
二人转对象
RelationHan大对象
```

所以：

# **关系是语义组织方式，不等于必须存在昂贵关系虚拟机。**

---

# 第六十章　设计模式为什么适合关系化

传统设计模式往往稳定的是：

```text
角色
信息传递
状态
控制变化
约束
失败
生命周期
```

这些恰好都可以转成关系。

因此设计模式可以被理解成：

```text
关系角色
+
字号端口
+
变化次序
+
不变量
+
失败语义
+
生命周期
```

而不是只记：

```text
几个类怎么画
```

---

# 第六十一章　观察者模式的关系化例子

传统：

```text
Subject
Observer
notify()
```

关系视角：

```text
状态变化号
↓
发布文字
↓
多个订阅关系
↓
观察文字
```

还要规定：

```text
订阅生命周期
失败隔离
背压
顺序
取消关系
```

因此比“回调列表”表达更完整。

---

# 第六十二章　策略模式的关系化例子

传统：

```text
Strategy接口
多个实现
```

关系视角：

```text
关系目标
↓
多个合法方法候选
↓
根据当前条件选择
↓
执行
```

方法选择和正式语义分离。

这与多Provider选择很相似。

---

# 第六十三章　状态模式的关系化例子

传统：

```text
State对象
状态切换
```

关系视角：

```text
当前有效状态
+
允许的雨变化
+
关限制
```

无需强制每个状态都成为一个对象类。

---

# 第六十四章　关系设计中的“不变量”

复杂关系最好明确写出：

```text
必须始终成立什么？
```

例如文件关系：

```text
关闭后不可读取
MOVE后原持有者不可访问
未结束借用时不可回收
```

这些不变量比“代码按什么顺序写”更重要。

---

# 第六十五章　关系设计中的“失败语义”

每个复杂关系都应该回答：

```text
失败发生在哪些阶段？
失败是否可重试？
失败后是否部分生效？
失败后谁回收？
失败是否改变Generation？
```

不要只写：

```text
失败返回false
```

---

# 第六十六章　关系设计中的“可恢复性”

例如网络请求失败：

```text
超时
```

可以：

```text
重试
切Provider
降级
返回失败
```

选择哪种行为，应该由当前关系政策决定。

---

# 第六十七章　有限重试，不要无限循环

如果当前方法失败，可以尝试其他合法方法。

但必须：

```text
候选有限
已尝试记录
预算有限
失败原因明确
```

不能：

```text
一直换方法直到碰巧成功
```

---

# 第六十八章　模型不足和方法失败要区分

例如：

```text
当前排序算法不合适
```

是：

```text
方法问题
```

而：

```text
当前模型根本无法表达这个资源约束
```

是：

```text
模型问题
```

二者后续处理不同。

高级机制中的三刀流会正式处理这种区分。

---

# 第六十九章　关系编程中的调试第一法：展开

看到：

```hanrain
*说 格式化 校验 解析 读取 路径；
```

出错时先展开：

```hanrain
原文* 读取 路径；
结构* 解析 原文；
结果* 校验 结构；
文本* 格式化 结果；
*说 文本；
```

然后逐边检查。

---

# 第七十章　调试第二法：给隐藏号命名

如果：

```text
到底是哪一个中间输出不对？
```

把它命名。

显式号是关系调试的最好工具之一。

---

# 第七十一章　调试第三法：查看端口

不要只看：

```text
A不能连接B
```

要看：

```text
A吐了哪些号？
B需要哪些端口？
哪一个端口没满足？
哪个号多出来？
```

---

# 第七十二章　调试第四法：检查长期能力和本场许可

如果：

```text
字明明存在
类型也对
```

仍然失败，检查：

```text
当前关系是否允许这个效果？
Provider是否提供？
资源是否允许？
```

---

# 第七十三章　调试第五法：检查生命周期

很多系统错误并不是类型错误，而是：

```text
太早释放
重复释放
旧世代访问
借用未归还
Pending未结束
```

这时要画生命周期，而不是继续修改类型。

---

# 第七十四章　关系测试应该测什么

不要只测：

```text
最终结果=7
```

还应该测：

```text
错误关系被拒绝
未处理失败被发现
MOVE后使用被拒绝
Provider切换语义一致
旧Generation不能访问
失败后资源回收
```

---

# 第七十五章　关系测试中的“负例”特别重要

因为关系系统最核心的能力之一是：

# **知道什么时候无权继续。**

所以应主动设计：

```text
类型错
端口错
资源错
权限错
世代错
生命周期错
```

验证编译器是否正确提前拒绝。

---

# 第七十六章　大型项目如何拆关系

不要构造一场覆盖整个系统的巨型关系。

更适合：

```text
局部关系
↓
形成稳定输出
↓
成为下一场关系输入
```

例如：

```text
读取关系
解析关系
校验关系
持久化关系
```

它们通过正式号和公共文字衔接。

---

# 第七十七章　什么时候应该形成新的正式文字

当一组关系：

```text
反复出现
边界稳定
输入输出稳定
失败稳定
值得独立测试
值得单独版本
```

可以封装为正式文字。

这就是：

```text
关系组合
↓
形成新的稳定自治计算主体
```

但仍遵循：

# **组合优先，增字从严。**

---

# 第七十八章　不要把每个关系都正名

临时的一次流程：

```text
只在一个函数里用
没有公共能力
没有独立版本需要
```

可以保持局部关系。

正式名字应留给：

```text
值得长期复用的稳定计算结构
```

---

# 第七十九章　不要制造“万能关系管理器”

常见反模式：

```text
RelationManager
GlobalRelationRuntime
EverythingCoordinator
```

让一个对象负责：

```text
名字
资源
调度
生命周期
错误
Provider
提交
```

这会破坏汉雨职责分离。

更合适：

```text
每个权威事实守自己的职责
关系只把它们有据地组织起来
```

---

# 第八十章　不要把所有关系都运行时动态化

如果：

```text
参与字固定
号类型固定
Provider固定
关系拓扑固定
```

应该尽量编译期确定。

动态机制只用于真正动态的部分。

---

# 第八十一章　不要让号决定全部语义

号可以影响：

```text
候选匹配
端口
值
状态
```

但不能单独决定：

```text
选择哪个正式字
扩大权限
创建本场许可
绕过关
```

原则：

# **号参与关系形成，但不拥有关系最终权威。**

---

# 第八十二章　不要让名字决定全部语义

同样：

```text
名字叫“安全写入”
```

不能证明：

```text
它真的安全
```

正式能力和关系证据才决定。

名字只是入口。

---

# 第八十三章　不要让性能绕过合法性

再快的实现，如果：

```text
类型不合法
权限不允许
Generation陈旧
所有权冲突
```

都不能使用。

性能优化只在合法空间里发生。

---

# 第八十四章　关系设计模板

可以用下面模板设计复杂关系：

```text
关系名称：

目标：

输入号：

成功输出：

失败输出：

参与正式字：

外部资源：

长期能力要求：

本场限制：

所有权：

生命周期：

Provider候选：

安全要求：

性能预算：

未决事项：

关闭条件：

回收条件：
```

这比只画调用图更适合汉雨。

---

# 第八十五章　示例：文件配置加载

```text
关系：
加载配置

输入：
路径

参与：
读取
解析
校验
提交

资源：
文件系统
配置存储

成功：
新配置已提交

失败：
文件失败
解析失败
校验失败
提交失败

所有权：
文件句柄在读取结束后释放

提交规则：
校验成功之前不得修改正式配置

关闭：
无Pending，无未释放句柄
```

关系图：

```text
路径
↓
读取
├─失败→诊断
└─文本
   ↓
  解析
  ├─失败→诊断
  └─结构
     ↓
    校验
    ├─失败→诊断
    └─合法配置
       ↓
      提交
```

# 第八十六章　示例：图片处理

需求：

```text
读取图片
缩放
编码
写文件
```

资源：

```text
输入文件
内存缓冲
输出文件
```

这里可以选择：

```text
CPU缩放
GPU缩放
```

但不应改变：

```text
缩放的正式语义
```

# 第八十七章　示例：异步网络请求

```text
请求号
↓
网络发送
↓
Pending
↓
响应到达
↓
解析
↓
结果
```

关系在：

```text
Pending
```

期间不能被误判为已经结束。

取消请求时，还要解决：

```text
网络资源
回调
超时
未决响应
```

# 第八十八章　示例：缓存

缓存命中：

```text
键
↓
查询
↓
值
```

缓存未命中：

```text
键
↓
查询
↓
无值
↓
计算/读取
↓
写缓存
↓
值
```

缓存只是：

```text
一种实现和优化关系
```

不能改变正式计算语义。

# 第八十九章　关系图和物理架构分开

同一关系：

```text
读取→解析→校验
```

可以运行在：

```text
单进程
多线程
多进程
远程服务
```

关系语义不应该因为物理部署方式变化而完全重写。

---

# 第九十章　进程、线程、协程只是实现承载

汉雨关系不以：

```text
进程
线程
协程
```

作为最高语义单位。

它们属于：

```text
某种Provider
调度方法
物理执行环境
```

关系可以投影到这些机制，但不被它们定义。

---

# 第九十一章　并发关系首先问“共享什么”

不要先问：

```text
开几个线程？
```

先问：

```text
哪些号共享？
哪些资源共享？
谁能写？
谁只读？
什么时候需要同步？
```

再决定：

```text
原子
锁
快照
串行
复制
```

---

# 第九十二章　关系可以跨机器

只要：

```text
公开能力
号格式
失败
安全
Generation
```

能够被明确描述，一场关系可以跨：

```text
进程
机器
网络
设备
```

但跨边界会增加：

```text
失败
延迟
版本
认证
恢复
```

这些必须进入关系需求。

---

# 第九十三章　关系的“边界”要尽量小

关系越大：

```text
参与者越多
状态越多
失败越多
证明越难
```

因此推荐：

# **小关系闭合，再组合成大关系。**

这类似模块化，但关系边界更强调：

```text
输入
输出
资源
失败
生命周期
```

---

# 第九十四章　关系不是“所有东西都互相连”

关系化不等于：

```text
建立全局大图
让所有字都能发现所有字
```

真正好的关系模型强调：

```text
候选有限
作用域明确
道路明确
权限明确
```

关系越有据，推理和编译越可靠。

---

# 第九十五章　关系编程的设计顺序

推荐顺序：

```text
1. 写目标
2. 写输入输出
3. 写失败
4. 查成熟字
5. 画字号图
6. 补资源和所有权
7. 补本场许可
8. 补生命周期
9. 决定Provider
10. 最后再缩写源码
```

而不是：

```text
先写一大段连字
然后等编译器告诉你什么意思
```

---

# 第九十六章　与三刀流、二人转的关系

普通关系编程时，只需要知道：

```text
复杂关系内部
编译器可能要：
过滤材料
比较方法
判断模型
构造有限候选
准备
提交
```

更深层的：

```text
乱刀
利刀
道刀
二人转
PreparedTurn
QKV-D
```

将在《高级关系机制》中解释。

重要边界：

# **这些机制帮助关系成立，不是用户每次都必须手写的新语法。**

---

# 第九十七章　与汉、雨的关系

普通用户可以保持两个简化理解：

```text
雨
准备完成的变化真正发生

汉
发生后，关系还能不能继续、关闭、回收
```

不要把：

```text
汉
雨
```

做成业务代码中无处不在的对象。

---

# 第九十八章　关系最终必须归机

编译器最终会把：

```text
正式文字
号绑定
关系边界
控制
值
```

逐步下降成：

```text
CFG
SSA
唯一HanRain MIR
C11 / LLVM / Native
机器
```

静态已经确定的高层关系信息，应尽可能消失。

这保证：

# **面向关系不等于牺牲原生执行。**

---

# 第九十九章　关系编程能力自测

如果你能解释下面十个问题，就已经掌握本册核心：

```text
1. 为什么关系不是一条裸边？
2. 字的自治边界在哪里？
3. 号除了值还能承载什么？
4. 长期能力和本场许可有什么区别？
5. 为什么类型相同仍可能不能绑定？
6. 为什么连字不是普通函数复合？
7. 为什么Prepared不能等于已经发生？
8. Pending为什么会影响关系回收？
9. Provider为什么不能决定正式语义？
10. 为什么静态关系最终可以没有运行时关系对象？
```

# 第一百章　最终心智模型

关系编程可以压缩成：

```text
目标
↓
寻找成熟字
↓
确认长期能力
↓
确定本场许可
↓
号与端口形成唯一绑定
↓
关系准备
↓
正式发生
↓
产生新号、新效果或失败
↓
检查未决义务
↓
继续 / 关闭 / 回收
```

而整个汉雨关系世界最核心的结构仍然是：

```text
号
↓
字
↓
号
↓
字
↓
号
```

只是每一条边都要回答：

```text
为什么能连？
谁允许？
谁拥有？
什么时候发生？
发生后还剩什么？
```

# 附录 A　关系编程速查表

|问题|优先检查|
|---|---|
|找不到能力|字库、名字、道路|
|字存在但不能用|长期能力、本场许可、Provider|
|两个字连不上|号、端口、类型、角色|
|类型对仍连不上|所有权、生命周期、Generation、效果|
|连字歧义|展开中间号、显式选择端口|
|失败没人接|Result/Option/失败出口|
|资源不能释放|Pending、借用、Obligation|
|热更新后旧引用失效|Generation|
|多个实现怎么选|关系要求 + Provider候选|
|性能优化能否采用|先合法，再择优|


# 结束语

面向关系不是要求程序员：

```text
把所有东西都画成关系图
```

而是形成一种更严格的提问顺序：

```text
先问要完成什么
再问谁能参与
再问什么号能够流动
再问当前关系允许什么
再问变化什么时候真正发生
最后问什么时候能够结束
```

字保持自治，号负责沟通，关系负责说明：

```text
为什么它们此时能够共同成立。
```

最终总句：

# **关系立其问，字守其能，号通其间；关限其界，中定其应，系行其路；雨使其成，汉守其续，能证则消，终归于机。**

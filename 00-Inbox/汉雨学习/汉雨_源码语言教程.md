# 第一章　汉雨源码到底在写什么

传统语言经常从：

```text
变量
表达式
函数
对象
语句
```

开始。

汉雨源码更适合先从：

```text
名字
字
号
关系
道路
```

开始理解。

一句最基本的汉雨源码：

```hanrain
和* 加 3，4；
```

可以读成：

```text
3、4
↓
加
↓
和
```

也就是：

> 让成熟文字“加”吃下两个号 `3` 和 `4`，把它吐出的结果号命名为“和”。

所以：

# **汉雨源码不是把符号拼成表达式，而是在描述字号关系。**

# 第二章　最重要的阅读规则

记住一句：

# **源码顺读，字句逆求；右侧备号，中字食化，左侧承果。**

## 2.1 源码整体仍然从左往右读

编译器正常读取：

```hanrain
和* 加 3，4；
```

识别出：

```text
左侧结果：和
当前文字：加
右侧输入：3、4
```

不需要把整个文件倒着扫描。

---

## 2.2 字句内部按依赖理解

真正的数据依赖是：

```text
先取得3和4
↓
加吃下
↓
产生结果
↓
结果由和承接
```

所以汉雨的“右吃左吐”是：

```text
求值和关系方向
```

不是：

```text
词法器倒着读文件
```



# 第四章　为什么姓使用 `~`

源码候选中：

```hanrain
~ 算
```

表示当前源码单元的“姓”。

选择 `~` 的目的，是让：

```text
~ # @
```

形成一套独立的身份冠符：

```text
~ 姓
# 氏
@ 名
```

这样可以释放传统的：

```text
-
```

不让它同时承担：

```text
姓
减法
负号
```

等多种职责。

因此本教程遵循：

# **`-` 不拥有汉雨核心减法语义。**

减法由成熟文字：

```text
减
```

承担。

例如：

```hanrain
差* 减 10，3；
```

而不是：

```hanrain
差* 10 - 3；
```

# 第五章　算术为什么写成字

基础算术推荐写成：

```hanrain
和* 加 7，5；
差* 减 7，5；
积* 乘 7，5；
商* 除 7，5；
余* 余 7，5；
```

这不是为了故意“中文化”。

而是为了保持一条统一原则：

# **符号管章法，文字管算法。**

加减乘除都是成熟文字。

它们可以拥有：

```text
正式身份
公开能力
类型要求
失败方式
版本
Provider
```

而不是另外建立一套：

```text
+ - * / %
```

作为平行的语言计算权威。

# 第七章　姓：源码的治理根

形式：

```hanrain
~ 算
```

可以把“姓”理解成：

> 当前源码单元在公共语义世界中的治理根和稳定来源根。

它主要帮助回答：

```text
这份源码属于哪里？
它产生的公共文字从哪里受生？
默认在哪个治理范围里？
跨文件身份从哪里开始？
```

不要把姓简单理解成：

```text
class
namespace
文件夹
包名
```

它和这些概念可能有部分对应，但职责不完全相同。

---

# 第八章　氏：能力和实现环境

形式：

```hanrain
# 计算
```

氏主要表示：

```text
能力域
资源域
实现域
Provider候选域
ABI或设备环境
```

例如：

```hanrain
~ 驱动

    # 网卡

    # 内存

    # 日志
```

这里：

```text
网卡
内存
日志
```

默认是平级的氏域。

不要因为缩进就认为：

```text
网卡拥有内存
内存继承日志
```

若存在真实关系，应显式建立。

---

# 第九章　名：公共入口

形式：

```hanrain
@ 简单加法
```

`@`表示一个公共名字候选。

关键边界：

# **写下名字，不等于已经形成成熟正式字。**

正式过程更接近：

```text
提出名字
↓
形成正文
↓
检查输入输出
↓
检查效果和失败
↓
验证关系
↓
正式提交
```

所以：

# **名先立其候，验文而后正名。**

# 第十章　最基本的字句

形式：

```hanrain
和* 加 3，4；
```

结构：

```text
[左侧输出号] * [中字] [右侧输入号]
```

可以抽象为：

```text
吐号列 * 字 吃号列；
```

因此：

```hanrain
和* 加 3，4；
```

表示：

```text
加
吃：3、4
吐：和
```

---

# 第十一章　没有左侧结果时

例如：

```hanrain
*说 文本；
```

表示：

```text
说吃下文本
```

而当前源码不需要为它的主要返回值命名。

最典型的是：

```text
终端输出
日志写入
资源提交
```

但是否真的“没有输出”，取决于该正式字的公开能力。

例如某些有副作用文字还可能产生：

```text
状态
Result
错误
句柄
```

如果这些必须处理，就不能静默忽略。

---

# 第十二章　多个输出

假设一个字：

```text
拆开
```

会吐：

```text
头
尾
```

显式写法可以是：

```hanrain
头 尾* 拆开 文本；
```

如果目标字只有一个输出：

```hanrain
和* 加 1，2；
```

单个结果名即可。

多个输出不能靠编译器任意猜。

---

# 第十三章　多个输入

输入可以用明确分隔：

```hanrain
和* 加 左，右；
```

如果输入本身是复杂关系，推荐先具名：

```hanrain
左值* 读取 左来源；
右值* 读取 右来源；
和* 加 左值，右值；
```

不要一开始追求极端缩写。

汉雨强调：

# **关系清楚优先于代码短。**

---

# 第十四章　数字、字符和文本

需要明确区分：

```text
1
'1'
"1"
```

它们分别应表示不同的号。

例如：

```text
1
整数值

'1'
字符

"1"
文本
```

因此：

```hanrain
结果* 解析整数 "123"；
```

与：

```hanrain
结果* 加 123，1；
```

不是同一种输入关系。

---

# 第十五章　成熟文字来自哪里

普通程序最常使用的字来自：

```text
初路
项目常路
显式引路
当前文件新形成的文字
```

例如：

```hanrain
引 标准——整数——加；
引 标准——终端——输出 为 说；
```

然后：

```hanrain
和* 加 3，4；
*说 和；
```

---

# 第十六章　`引`：让当前源码看见成熟文字

形式：

```hanrain
引 标准——整数——加；
```

它表示：

> 当前源码获得对该正式文字的可见入口。

它不会：

```text
复制这个字
重新定义这个字
执行这个字
更改这个字
```

只是建立可见关系。

---

# 第十七章　完整道路和局部称呼

完整道路：

```text
标准——终端——输出
```

正文中可以简写成：

```hanrain
引 标准——终端——输出 为 说；
```

以后：

```hanrain
*说 "你好"；
```

这里：

```text
标准——终端——输出
确定正式所指

说
当前源码局部称呼
```

所以：

# **道路定其身，称呼便其用。**

---

# 第十八章　语义道路不是文件路径

例如：

```text
标准——整数——加
```

可能物理存放在：

```text
src/std/int/add.mh
```

以后移动到：

```text
lib/core/math/add.mh
```

只要正式身份没变化，道路可以不变。

因此：

```text
——
```

表示语义道路，不是：

```text
/
\
::
.
```

的中文替代。

---

# 第十九章　定义自己的文字

最小形式：

```hanrain
*求和 左 右：
    *加 左，右；
```

可以理解成：

```text
名字：求和

输入：
左
右

正文：
调用“加”
```

如果需要产生明确结果：

```hanrain
*求和 左 右：
    和* 加 左，右；
    *归 和；
```

---

# 第二十章　定义不等于立即发布

源码里出现：

```hanrain
*求和 左 右：
```

表示开始形成一段文字。

只有当正文满足：

```text
输入完整
输出完整
类型合法
失败合法
效果合法
资源合法
关系闭合
```

之后，它才可能成为正式可复用文字。

因此编译错误不会留下：

```text
半成熟FormalZi
半条道路
污染的字库条目
```

这属于工具链保证。

---

# 第二十一章　调用自己的文字

定义：

```hanrain
*求和 左 右：
    和* 加 左，右；
    *归 和；
```

调用：

```hanrain
结果* 求和 3，4；
```

关系：

```text
3、4
↓
求和
↓
结果
```

如果编译器最终证明：

```text
求和
只是加的透明封装
```

它可以被内联或擦除。

源码结构和机器结构不必一一对应。

---

# 第二十二章　局部文字和正式文字

不是所有文字都必须进入公共字库。

局部文字可以只服务当前文件或当前正式字。

例如：

```hanrain
*整理 输入：
    ...
```

如果它：

```text
不需要跨文件引用
不需要独立版本
不需要公共能力边界
```

就可以保持局部。

只有需要：

```text
跨文字调用
跨文件引用
单独版本化
公共文档
独立能力边界
```

时，才需要进入正式正名流程。

---

# 第二十三章　连字是什么

普通写法：

```hanrain
原温* 读温 传感器；
摄氏* 转摄氏 原温；
文本* 加单位 摄氏；
*说 文本；
```

关系明确以后，可以缩写：

```hanrain
*说 加单位 转摄氏 读温 传感器；
```

这就是连字。

---

# 第二十四章　连字最重要的原则

# **连字省号名，不省号。**

内部仍然是：

```text
传感器
↓
读温
↓ h0

h0
↓
转摄氏
↓ h1

h1
↓
加单位
↓ h2

h2
↓
说
```

所以源码表面：

```text
字 字 字 字
```

内部仍然能够恢复成：

```text
字 → 号 → 字 → 号 → 字
```

---

# 第二十五章　连字不是普通函数复合

不要简单认为：

```hanrain
*甲 乙 丙；
```

必然只是：

```text
甲(乙(丙))
```

编译器还要判断：

```text
乙吐什么号
甲能吃哪些号
多个输出怎样匹配
所有权是否合法
失败出口怎样承接
效果次序是否合法
Generation是否有效
```

因此连字是：

# **相邻成熟文字之间的关系转位。**

---

# 第二十六章　什么时候适合连字

适合：

```text
关系短
中间结果唯一
类型清楚
失败简单
资源关系简单
```

例如：

```hanrain
*说 格式化 加 3，4；
```

---

# 第二十七章　什么时候不要连字

如果存在：

```text
多个输出
Result/Option
资源所有权
生命周期
多个Provider
复杂失败
异步等待
调试需求
```

优先展开：

```hanrain
原文* 读取 路径；
解析结果* 解析 原文；
报告* 校验 解析结果；
*说 报告；
```

经验：

# **读不清楚，就把隐藏号重新写出来。**

---

# 第二十八章　同名文字如何消歧

假设同时存在：

```text
标准——整数——加
标准——浮点——加
项目——矩阵——加
```

源码：

```hanrain
结果* 加 左，右；
```

编译器会利用：

```text
输入号类型
预期输出
当前氏域
公开能力
当前关系限制
```

缩小候选。

如果仍然不能唯一确定：

```text
必须报歧义
```

用户可以：

```hanrain
引 标准——整数——加 为 整数加；
```

然后：

```hanrain
结果* 整数加 左，右；
```

---

# 第二十九章　源码里不要直接操作内部UID

普通源码应该写：

```text
名字
道路
号
```

而不是：

```text
FormalZiUID=...
NatureVersion=...
RelationUID=...
HaoBindingId=...
```

这些内部身份负责：

```text
稳定性
缓存
链接
调试
关系证据
```

但不属于普通编程表面。

---

# 第三十章　条件关系

汉雨最终需要表达：

```text
条件成立
→ 走一条关系

条件不成立
→ 走另一条关系
```

使用者应先理解语义，而不是背某个暂未冻结的表面符号。

核心结构：

```text
条件号
↓
判断文字
↓
真路 / 假路
```

例如概念上：

```text
温度
↓
比较阈值
├─ 高 → 报警
└─ 低 → 继续
```

条件结构属于：

```text
ControlRegion / CFG
```

而不是让某个号本身偷偷决定全部控制流。

---

# 第三十一章　为什么控制结构不能只靠连字

连字主要解决：

```text
相邻文字之间的数据传递
```

条件和循环还要表达：

```text
哪个块先执行
哪个块可能不执行
哪条边是回边
哪个出口结束
```

所以：

```text
连字
不能替代
条件 / 循环 / CFG
```

---

# 第三十二章　循环关系

循环可以理解成：

```text
初始号
↓
文字处理
↓
判断是否达到条件
├─ 否 → 回到处理
└─ 是 → 输出结果
```

汉雨内部可以使用：

```text
CFG
SSA
循环回边
```

表达。

用户不需要把循环解释成：

```text
某个字自己无限吃自己
```

---

# 第三十三章　“写、学、生”不是普通循环关键字

高级设计中：

```text
写
学
生
```

有特殊关系意义。

但普通源码使用者不要把它们直接等价成：

```text
if
while
for
```

更准确地说：

```text
写
当前关系可以直接闭合

学
当前模型内有限换法

生
当前模型不足时有界升模
```

这些属于高级关系机制。

---

# 第三十四章　Result 怎么理解

一个可能失败的文字，可以产生：

```text
成功
或
失败
```

例如：

```text
解析整数
```

输入：

```text
"123"
```

可能得到：

```text
整数123
```

输入：

```text
"abc"
```

可能得到：

```text
格式错误
```

用户必须明确：

```text
成功谁接
失败谁接
```

---

# 第三十五章　Option 怎么理解

一个关系可能：

```text
有结果
或
没有结果
```

例如：

```text
在集合中查找满足条件的元素
```

结果：

```text
Some(值)
```

或：

```text
None
```

不能把：

```text
没有结果
```

偷偷解释成：

```text
0
空字符串
假
```

除非正式语义明确如此规定。

---

# 第三十六章　未处理失败为什么应该报错

例如：

```hanrain
数据* 读取 路径；
```

如果“读取”可能失败，而源码完全不处理失败出口，编译器应该提醒或拒绝。

因为：

```text
失败也是正式关系结果
```

不是：

```text
可有可无的日志消息
```

这对系统编程尤其重要。

---

# 第三十七章　资源文字

例如：

```text
打开文件
读取文件
写文件
关闭文件
```

它们不只是纯函数。

可能涉及：

```text
句柄
所有权
借用
生命周期
外部效果
失败
Provider
```

因此建议显式写中间号：

```hanrain
文件* 打开 路径；
数据* 读取 文件；
*关闭 文件；
```

不要一开始用超长连字隐藏资源关系。

---

# 第三十八章　COPY、MOVE、BORROW 的用户直觉

可以先粗略理解：

```text
COPY
复制后双方都能继续使用

MOVE
转移后原持有者不能继续使用

BORROW
临时借用，所有权仍在原持有者
```

例如某个号被 MOVE：

```text
A拥有资源
↓
MOVE给B
↓
A不可继续使用旧资源
```

这不是额外的“安全检查装饰”，而是关系是否合法的一部分。

# 第三十九章　为什么号会带Generation

动态资源、插件或热更新环境中，同一个公开名字可能在不同时间指向：

```text
Generation 7
Generation 8
```

旧引用不能自动继续访问新实例。

因此编译器或运行时会检查：

```text
当前号是不是来自正确世代
```

普通用户通常只在动态系统里遇到这类诊断。

# 附录 A　核心符号速查

|---|---|

```text

不承担减法正式语义

不承担乘法正式语义

乘
才是乘法成熟文字
```

# 结束语

汉雨源码最重要的不是“中文符号长什么样”，而是：

```text

道路提供依据
```

# **源码顺读，字句逆求；右侧备号，中字食化，左侧承果。**

# **符号定章法，名字认其字；道路定所指，字号成关系；能证则消，终归于机。**

# 汉雨 HanRain《字库使用手册》

## ——成熟字有其身，名字循路而见；能组合则组合，确有新义方正名

**文档性质：** 用户手册  
**适用阶段：** 汉雨正式字库、号库已完成持久化并随发行包或项目环境可稳定装载  
**主要读者：** 汉雨应用开发者、库使用者、项目维护者  
**不要求读者预先掌握：** FormalZi、Nature、Mandate、HaoBinding、三刀流、二人转、RelationHan、RainCommit、CFG、SSA、MIR  
**本文目标：** 让使用者能够查字、辨字、引字、用字、组合字，并判断什么时候应该复用已有文字、什么时候才应该形成新的正式字

> 本手册只讲“怎样使用持久化后的字库”。  
> 姓、氏、名的最终源码冠符、完整控制语法等表面语法，以《源码语言教程》和实际发行版为准。本文不依赖尚未完全冻结的姓声明符号。

# 一、先理解：汉雨的“字库”不是什么

第一次接触汉雨字库时，不要把它理解成下面任何一种东西：

```text
函数大全
运行时对象仓库
动态脚本字典
每次调用都要查询的数据库
关键词表
ASCII运算符映射表
```

汉雨字库更接近：

> **正式文字的长期语义注册体系。**

一个已经进入字库的成熟文字，至少意味着：

```text
它是谁
怎样被人引用
长期能够吃什么
长期能够吐什么
可能产生什么效果
可能怎样失败
对资源和所有权有什么要求
属于哪个稳定语义道路
处于什么版本
有哪些别名或兼容称呼
```

因此：

# **字库保存的不是“代码片段”，而是已经取得稳定身份和公开能力的成熟文字。**

---

# 二、为什么完成持久化以后，汉雨才真正适合普通使用者

在没有稳定持久化字库时，编译器每次面对：

```text
加
减
说
解析
读取
排序
```

都必须重新回答：

```text
这个名字是谁？
它是不是以前那个字？
它的公开能力是什么？
它在哪里？
它换了文件以后还是不是同一个字？
当前项目能不能看见它？
```

完成持久化以后，工具链可以长期保存和恢复：

```text
稳定文字身份
公开名字
语义道路
长期能力
版本
索引
形成证据摘要
```

于是使用者看到的是：

```text
“加”已经存在
“输出”已经存在
“解析”已经存在
```

你不需要每个项目重新制造这些成熟能力。

持久化真正带来的用户价值是：

# **成熟字已经在那里；你要做的是找到它、确认它、引入它，然后让它参与当前关系。**

---

# 三、用户真正接触的四个入口

普通使用者使用字库时，主要接触四个概念：

```text
名字
道路
公开能力
版本
```

内部稳定 UID、稠密索引、缓存键等属于编译器和数据器。

可以把一次正常取字理解成：

```text
人看到名字
↓
名字位于语义道路
↓
编译器找到正式文字
↓
读取它的公开能力
↓
当前源码取得可见入口
↓
实际字句使用该文字
```

而不是：

```text
用户手写UID
↓
直接访问Registry内部结构
```

---

# 四、名字：你怎样称呼一个成熟字

## 4.1 名字不是文字本体

假设字库中存在一个正式文字：

```text
标准——终端——输出
```

它的规范公共名可能是：

```text
输出
```

当前文件可以给它一个更自然的局部称呼：

```hanrain
引 标准——终端——输出 为 说；
```

正文中：

```hanrain
*说 文本；
```

这里：

```text
输出
正式公共名字

说
当前源码中的局部称呼
```

二者指向同一个成熟文字。

因此：

# **换称呼，不等于换了字。**

---

## 4.2 多个名字可以指向同一个字

同一个正式文字可以拥有：

```text
规范名
中文别名
历史兼容名
外语别名
FFI桥接名
项目局部称呼
```

这些名字不应该各自拥有一份：

```text
正文
长期能力
正式身份
版本
```

如果它们只是称呼关系，它们应共同指向同一个正式文字。

例如：

```text
标准——整数——加
```

在不同环境中可能被称为：

```text
加
求和
sum
add
```

但名字相同或相近，本身不能证明是同一个字；最终仍由正式道路和稳定身份确定。

---

# 五、道路：真正决定“你说的是谁”

## 5.1 语义道路不是物理文件路径

正式道路例如：

```text
标准——整数——加
```

它可以映射到某个物理源码文件：

```text
src/std/int/add.mh
```

以后项目重整，将文件移动到：

```text
lib/core/arithmetic/add.mh
```

只要正式文字身份没有变化，其语义道路仍然可以保持：

```text
标准——整数——加
```

因此：

# **道路回答“它在语义上是谁”，目录回答“文件现在放在哪里”。**

不要把两者混为一谈。

---

## 5.2 为什么这很重要

如果“文件路径 = 文字身份”，那么：

```text
移动目录
重命名文件夹
拆分仓库
调整工程结构
```

都可能导致大批文字被误判为“新字”。

汉雨把语义道路与物理位置分开，是为了使：

```text
身份稳定
增量编译准确
缓存可复用
跨项目引用可靠
调试信息可追溯
```

---

## 5.3 道路引用的基本原则

声明一个文字时，源码可能使用姓、氏、名等结构建立它的正式道路。

引用时，不需要重新书写这些声明冠符。

候选写法：

```hanrain
引 标准——整数——加；
```

可读作：

> 当前源码取得“标准 → 整数 → 加”这个正式名字的可见入口。

它不会：

```text
重新创建“加”
复制“加”
修改“加”的能力
执行“加”
```

只是让当前源码能够引用它。

---

# 六、初路：为什么有些字不用显式“引”

某些极小、普遍、经过版本审议的成熟文字，可以进入语言的“初路”。

例如，一个语言版本可能使：

```text
归
```

默认可见。

表面上：

```hanrain
*归 结果；
```

好像“归”没有完整身份。

实际上它仍然可以有完整道路，例如：

```text
初——控制——归
```

只是当前语言环境已经预先将它加入最小可见集合。

所以：

# **通用字不是无名，乃是其名已在初。**

---

## 6.1 初路必须保持极小

初路不应该变成：

```text
万能全局命名空间
全部标准库自动导入
所有设备和网络能力默认可见
所有并发能力默认可见
```

否则：

```text
名字冲突增加
候选域膨胀
关系推断变重
用户难以知道能力从何而来
```

比较合适的初路只包含语言普遍必需、稳定且可审计的最小能力。

---

# 七、项目常路：项目自己的“常用地区”

大型项目通常会长期使用一组固定能力。

例如：

```text
标准——文本
标准——集合
项目——数据
项目——日志
```

这些能力可以形成项目级的常用可见集合。

项目常路和初路不同：

```text
初路
由语言版本和基础环境决定

项目常路
由当前工程决定
```

用户仍应能够追溯：

```text
某个名字为什么在当前文件可见
它来自初路
还是项目常路
还是显式引路
```

---

# 八、显式引路：最清楚、最可靠的取字方式

如果当前文件需要一个没有自动可见的成熟文字，最清楚的方式是显式引路。

例如：

```hanrain
引 标准——整数——加；
```

然后：

```hanrain
和* 加 3，4；
```

这条关系可以理解为：

```text
3、4
↓
加
↓
和
```

显式引路最大的价值不是“让代码能运行”，而是让依赖关系清楚：

```text
当前源码依赖哪个正式文字
依赖来自哪条道路
名字冲突时如何消歧
增量编译时哪条边应该失效
```

---

# 九、局部称呼：让代码更自然，但不改变身份

完整道路适合精确定位：

```text
标准——终端——输出
```

正文里反复书写它会很重。

可以使用局部称呼：

```hanrain
引 标准——终端——输出 为 说；
```

以后：

```hanrain
*说 "你好，汉雨"；
```

局部称呼只在当前作用域内有效。

它不能改变目标正式文字的：

```text
稳定道路
正式身份
长期能力
版本
ABI
Provider
```

可以记成：

```text
完整道路
负责“你到底是谁”

局部称呼
负责“我现在怎么叫你”
```

# 十、怎样看懂一个正式字的字库条目

一个面向用户的正式字条目，建议至少展示以下信息。

---

## 10.1 规范名字

例如：

```text
加
```

回答：

> 日常应该怎样称呼这个正式文字？

---

## 10.2 完整道路

例如：

```text
标准——整数——加
```

回答：

> 当名字发生冲突时，我到底指的是哪个“加”？

---

## 10.3 别名

例如：

```text
求和
sum
add
```

回答：

> 还有哪些受支持的称呼？

---

## 10.4 简要语义

例如：

```text
对两个整数执行规定溢出语义下的加法。
```

回答：

> 这个字长期负责什么？

---

## 10.5 输入端口

例如：

```text
左：整数
右：整数
```

回答：

> 它原则上可以吃什么？

---

## 10.6 输出端口

例如：

```text
结果：整数
```

回答：

> 它原则上会吐出什么？

---

## 10.7 效果

例如：

```text
纯计算
```

或：

```text
终端输出
文件读取
修改资源
```

回答：

> 使用它是否会改变外部世界？

---

## 10.8 失败

例如：

```text
无
```

或：

```text
路径不存在
权限不足
格式错误
溢出
```

回答：

> 哪些情况必须被当前关系处理？

---

## 10.9 所有权和生命周期

例如：

```text
COPY
BORROW
MOVE
```

回答：

> 输入号进入这个字以后，原来的持有者还能不能继续使用？

---

## 10.10 资源或 Provider 要求

例如：

```text
需要终端Provider
需要文件系统Provider
需要某种ABI
```

回答：

> 这个字在什么现实环境里才能真正工作？

---

## 10.11 版本与状态

例如：

```text
稳定
实验
弃用
兼容
```

回答：

> 当前是否适合继续使用？升级时需要注意什么？

# 十一、长期能力与“这一次能不能用”不是一回事

正式字的字库条目描述的是它的长期公开能力。

例如“读取”可能长期支持：

```text
路径输入
字节流输出
权限失败
路径失败
文件系统效果
```

但这不意味着任何关系中都可以随意使用“读取”。

当前关系还会受到：

```text
当前目标
当前资源
当前安全边界
当前Provider
所有权
Generation
效果政策
```

限制。

因此用户应该区分：

```text
“这个字原则上能做什么”
和
“这次关系实际上允许它做什么”
```

前者属于字库长期能力。

后者属于当前关系。

普通字库使用者不需要直接编辑内部 Mandate，但要理解：

# **字库说“能”，不等于当前关系一定说“可以”。**

---

# 十二、术码：可以帮助找字，但不能替代正式语义

字库可以从正式字的长期能力中派生术码，用于：

```text
快速分桶
候选筛选
搜索
索引
缓存
```

例如用户查找：

```text
整数
纯计算
双输入
单输出
```

术码可以帮助快速缩小候选范围。

但术码不是最终语义权威。

不能因为两个字术码相似，就认为：

```text
它们可以互换
它们的端口完全兼容
它们拥有同样权限
它们一定适合当前关系
```

最终仍需要读取完整的正式字能力和关系条件。

可以记成：

# **术码负责快找，正式能力负责定真。**

---

# 十三、怎样查字：推荐的四种搜索方式

一个成熟的字库界面至少应该支持四种查找思路。

## 13.1 按名字查

适合你已经大概知道要什么：

```text
加
解析
读取
排序
输出
```

---

## 13.2 按道路查

适合名字存在冲突：

```text
标准——整数——加
标准——浮点——加
项目——矩阵——加
```

这时不要依靠“哪个先搜到”决定。

---

## 13.3 按能力查

例如：

```text
输入：文本
输出：整数
失败：格式错误
效果：纯
```

用于寻找：

```text
解析整数
```

这种场景比只搜文字名字更可靠。

---

## 13.4 按领域或用途查

例如：

```text
数值
文本
集合
文件
网络
终端
时间
资源
并发
```

适合学习标准字库或探索已有能力。

---

# 十四、一个名字出现多个候选怎么办

假设当前作用域里同时存在：

```text
标准——整数——加
标准——浮点——加
项目——矩阵——加
```

只写：

```hanrain
结果* 加 左，右；
```

编译器可以利用：

```text
输入号类型
预期输出
当前领域
公开能力
当前关系约束
```

缩小候选。

如果最终仍然有多个同样合法的候选：

# **必须报告歧义，而不是随便挑一个。**

用户此时应：

```text
写完整道路
或
建立明确局部称呼
或
增加足以消歧的关系信息
```

汉雨的相对解名原则是：

# **名称可以相对，身份不能漂移。**

---

# 十五、多个名字什么时候只是别名，什么时候真的形成了新字

这是扩展字库时最容易犯错的地方。

例如：

```text
求和
```

只是对已有“加”的另一种称呼。

如果：

```text
输入相同
输出相同
效果相同
失败相同
资源要求相同
所有权相同
```

那么它更适合成为：

```text
别名
局部称呼
可擦除的关系投影
```

而不是新正式字。

---

如果你定义：

```text
安全求和
=
检查溢出
+
执行加法
+
新增失败出口
```

那么它已经增加了：

```text
新的检查
新的失败语义
新的关系结构
```

它才更可能形成真正新的组合文字。

因此：

# **新名字不必然产生新字；新的稳定语义结构才可能产生新字。**

---

# 十六、最重要的扩展原则：组合优先，增字从严

完成持久化以后，字库最危险的问题不是“字不够”，而是：

```text
每个项目都往基础字库加字
每个小包装都登记为正式字
同义字不断膨胀
已有组合能力被重复实现
```

最终会变成：

```text
几千个只差一点点的函数名
```

这会削弱汉雨真正希望得到的关系组合能力。

因此建议把下面这条作为字库使用第一原则：

# **凡能由现有正式文字通过连字、号绑定、关系组合和既有关系模板稳定收敛实现的功能，不新增基础正式字。**

---

# 十七、什么时候值得新增正式字

一个能力至少满足下列多数条件，才值得进入正式字库：

```text
具有独立语义
语义长期稳定
跨多个场景反复使用
输入输出边界明确
失败方式明确
效果边界明确
资源要求明确
不能简单视为已有字的别名
不能由非常短且稳定的现有组合完全替代
值得单独版本化
值得单独形成公共文档
```

可以做一个判断：

```text
只是方便少写几行？
→ 更可能是局部组合或别名

形成了新的公共能力边界？
→ 才考虑正式字
```

---

# 十八、项目字与基础字不要混在一起

不是所有正式文字都必须进入语言基础字库。

建议区分：

```text
语言基础字
标准字库字
领域扩展字
项目正式字
局部文字
```

例如：

```text
某业务项目里的“计算季度退款”
```

即使它是项目内稳定的正式文字，也没有必要进入语言标准字库。

而：

```text
整数加
文本解析
Result处理
文件读取
```

更可能属于通用标准能力。

可以记成：

# **正式，不等于标准；稳定，不等于全世界都需要。**

---

# 十九、跨文件只能正常引用公共名字

普通源码之间的正常关系是：

```text
源码甲
公开正式名字
↓
源码乙通过道路引入
↓
编译器找到正式文字
↓
具体号通过公开端口往来
```

普通源码不应该直接：

```text
抓取另一个文件的匿名正文
读取另一个文字的局部号
读取另一个文字的私有状态
```

原则为：

# **源码引名，编译器据名取字；号循名字的端口往来。**

---

# 二十、同一目录不意味着自动可见

两个文件都放在：

```text
src/math/
```

并不意味着：

```text
彼此自动引入
彼此自动共享名字
彼此自动共享局部号
```

可见性来自：

```text
正式公共名字
语义道路
显式引路
项目常路
语言初路
```

而不是磁盘距离。

这是理解大型汉雨工程非常重要的一点。

---

# 二十一、版本升级时，使用者应该关心什么

持久化字库必须让用户能够判断：

```text
这个名字是否仍然存在
道路是否变化
旧名字是否只是被弃用
公开端口是否变化
失败方式是否变化
效果是否变化
所有权规则是否变化
是否仍与旧版本兼容
```

最理想的升级情况是：

```text
实现变化
但公开长期能力保持兼容
```

那么使用者通常不需要修改源码。

如果改变的是：

```text
公开输入
公开输出
失败
效果
所有权
```

就属于真正的语义兼容性变化。

---

# 二十二、弃用与迁移

标准字库不应直接删除一个长期公开名字而不给迁移信息。

建议至少区分：

```text
ACTIVE
当前推荐

DEPRECATED
仍可用，但建议迁移

COMPATIBILITY_ALIAS
兼容旧名

REMOVED
当前版本不再提供
```

如果：

```text
旧——整数——求和
```

迁移为：

```text
标准——整数——加
```

工具应该能够明确告诉用户：

```text
旧道路
新道路
是否同一个正式字
是否只是别名迁移
是否存在语义变化
```

---

# 二十三、持久化不意味着运行时背着整个字库

这是非常重要的性能边界。

项目加载和编译时可以进行：

```text
读取持久字库
建立语义道路索引
建立名字索引
选择正式文字
验证公开能力
形成精确依赖边
```

随后驻留为更紧凑的：

```text
PathID
NameID
ZiIndex
```

进入正式编译以后，可以继续下降为：

```text
直接调用
内联
SSA值
函数地址
资源句柄
机器指令
```

因此不应该设计成：

```text
每调用一个“加”
→ 搜索Unicode字符串
→ 查询数据库
→ 创建FormalZi运行时对象
→ 再执行
```

正确原则是：

# **字库贯穿编译，静态查定后尽量退出运行热路径。**

---

# 二十四、字库持久化后，缓存和索引是什么地位

字库可以拥有很多索引：

```text
道路索引
名字索引
别名索引
术码索引
端口索引
效果索引
失败索引
能力索引
版本索引
弃用索引
```

这些索引的目的都是：

```text
更快找到候选
```

它们不能因为“命中了缓存”就获得新的语义权力。

例如：

```text
缓存认为A最像
```

不能替代：

```text
A的正式能力确实满足当前关系
```

可以记成：

# **索引能帮你找到答案，不能替你创造答案。**

# 二十五、字库使用中的常见错误

## 25.1 只搜短名字，不看完整道路

结果：

```text
选错同名文字
```

解决：

```text
出现歧义时查看完整道路
```

---

## 25.2 把别名当成新字

结果：

```text
重复造字
标准字库膨胀
```

解决：

```text
先比较输入、输出、效果、失败和资源语义
```

---

## 25.3 把文件路径当语义身份

结果：

```text
项目重构时误认为大量文字变更
```

解决：

```text
区分SemanticPath与SourceFile
```

---

## 25.4 看到功能就往基础字库加字

结果：

```text
失去组合收敛能力
```

解决：

```text
优先使用已有正式字、连字和关系组合
```

---

## 25.5 认为“字库有这个字”就表示当前一定能使用

结果：

```text
忽略资源、Provider、安全、所有权等关系限制
```

解决：

```text
区分长期能力与本场许可
```

# 二十六、遇到“找不到字”时怎么排查

按以下顺序检查：

```text
1. 名字是否写对？
2. 当前名字是否只是别名？
3. 完整道路是什么？
4. 当前源码是否能够看见该道路？
5. 是否需要显式引路？
6. 项目常路是否配置正确？
7. 当前语言版本是否仍提供该字？
8. 该字是否已弃用或迁移？
9. 当前使用的是不是另一个同名字？
```

不要第一反应就：

```text
重新造一个同名字
```

---

# 二十七、遇到“能找到但不能用”时怎么排查

这通常不是字库索引问题，而是关系问题。

检查：

```text
输入号类型
必需端口
输出端口
失败出口
效果
所有权
生命周期
Generation
资源Provider
当前安全边界
```

因此：

```text
找到这个字
≠
当前关系已经成立
```

这类问题会在《关系编程教程》和《错误诊断手册》中进一步展开。

# 二十八、推荐的日常工作流

一个普通汉雨开发者使用字库时，可以形成如下习惯：

```text
先明确需要什么能力
↓
按名字 / 道路 / 能力搜索
↓
查看正式字条目
↓
确认输入、输出、效果和失败
↓
优先引入已有成熟字
↓
先用显式号把关系写清
↓
关系稳定后再使用连字缩写
↓
确实没有合适能力时
再考虑形成项目新字
↓
跨项目长期稳定后
才讨论进入标准字库
```

# 二十九、一个完整示例：从查字到使用

假设需求：

> 把两个整数相加，然后输出结果。

首先查找：

```text
加
```

得到：

```text
标准——整数——加
```

再查找输出能力：

```text
标准——终端——输出
```

当前源码显式引入：

```hanrain
引 标准——整数——加；
引 标准——终端——输出 为 说；
```

使用：

```hanrain
和* 加 3，4；
*说 和；
```

这里完成了：

```text
3、4
↓
正式文字：标准——整数——加
↓
和
↓
正式文字：标准——终端——输出
```

整个过程没有：

```text
重新定义“加”
重新定义“输出”
访问字库内部UID
运行时扫描道路字符串
```

这就是持久化字库最典型的使用方式。

---

# 三十、另一个示例：同名“加”的消歧

假设字库存在：

```text
标准——整数——加
标准——浮点——加
标准——文本——加
项目——矩阵——加
```

如果当前源码只写：

```hanrain
结果* 加 左，右；
```

而输入关系已经明确：

```text
左：整数
右：整数
结果：整数
```

编译器可以唯一找到：

```text
标准——整数——加
```

如果输入和预期不足以唯一判断，就必须让用户明确指定：

```hanrain
引 标准——整数——加 为 整数加；
```

然后：

```hanrain
结果* 整数加 左，右；
```

原则是：

# **可以自动缩小候选，但不能自动猜测歧义。**

---

# 三十一、什么时候不要查“名字”，而要查“能力”

有时你不知道某个字叫什么，只知道自己需要：

```text
输入：文本
输出：整数
失败：格式错误
效果：纯
```

这时最合理的不是猜：

```text
转
换
解
读
析
```

而是按能力搜索。

字库真正成熟以后，能力搜索应该成为重要入口。

这也是为什么字库不是简单函数列表：

# **汉雨查字既可以从“叫什么”出发，也可以从“能做什么”出发。**

---

# 三十二、为什么文化字义可以帮助查找，但不能决定语义

汉雨可以保留：

```text
说文来源
字族
古义
文化索引
软关系
```

这些内容非常适合：

```text
辅助命名
解释设计来源
帮助发现相关文字
改善教学
```

但它们不能直接决定：

```text
端口类型
权限
所有权
当前关系是否合法
最终调用哪个FormalZi
```

可以记成：

# **文化索引帮助理解，正式能力决定计算。**

---

# 三十三、面向标准字库贡献者的最低要求

如果你准备把一个项目字提交到标准字库，至少应该回答：

```text
为什么它不是现有字的别名？
为什么现有组合不足以稳定替代？
它的语义能否长期保持稳定？
输入和输出是否明确？
失败是否明确？
效果是否明确？
资源要求是否明确？
所有权和生命周期是否明确？
名字是否足够稳定？
道路应该放在哪里？
版本兼容策略是什么？
```

如果其中很多问题无法回答：

```text
它更适合先作为项目内部文字
```

# 三十五、最重要的五条规则

如果读完整本手册后只保留五条：

## 第一条

# **名字用于称呼，正式道路用于确定所指。**

## 第二条

# **文件移动不应该自动改变正式字身份。**

## 第三条

# **能在字库中找到一个字，不代表当前关系一定允许使用它。**

## 第四条

# **能组合解决，就优先组合；确有独立稳定新义，才形成新字。**

## 第五条

# **字库服务编译与关系形成，不应成为每次运行都查询的动态数据库。**

# 结束语

持久化字库完成以后，汉雨使用者不应该天天思考：

```text
如何注册一个对象
如何维护一个数据库
如何手写UID
如何管理内部索引
```

更自然的工作方式应该是：

```text
我需要什么能力？
↓
字库里有没有成熟字？
↓
它在哪条道路？
↓
它能吃什么、吐什么？
↓
当前关系能不能使用它？
↓
能否与已有字组合完成目标？
```

这就是字库面向使用者真正应该提供的体验。

# **成熟字有其身，名字循路而见；能组合则组合，确有新义方正名。**

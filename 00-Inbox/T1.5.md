# Shadow Guard T1.5：Metabolic Tentacle Guard Runtime 详细介绍与标准族文件

## 0. 版本摘要

项目名称：Shadow Guard T1.5  
中文名称：Shadow Guard T1.5 代谢型触手旁路守护运行时  
英文建议名：Metabolic Tentacle Guard Runtime  
核心方向：工程证据链、风险准入、报告与胶囊生命周期管理、CI 工作流编排、Agent/CodeX MCP 工具层  
推荐实现语言：C++20 为主，Python / Shell / CMake / YAML / JSONL / SQLite 辅助  
目标环境：Windows + WSL2 Ubuntu、Linux 本地开发环境、远程 Linux/边缘主机、StarryOS/RK3588 板端验证链路、Asking Star 运行时旁路观测链路

一句话定义：

```text
Shadow Guard T1.5 是在 T1 触手型旁路守护运行时基础上，加入 ShadowMetabolism 代谢系统、CapsuleHeat 胶囊热度系统、RetentionPolicy 保留策略和 CI-MCP 编排层的工程证据链运行时。
```

更通俗地说：

```text
T1 让 Shadow Guard 看得见、记得住、能准入、能报告；
T1.5 让 Shadow Guard 会清理、会筛选、会归档、会复用经验、会帮助 Agent/CodeX 安排测试。
```

# 1. 版本定位

## 1.1 T1 已经解决的问题

Shadow Guard T1 的核心目标是把开发、构建、插件、远程、主板启动、短路降级和经验沉淀统一成一套旁路证据链。

T1 的核心链路是：

```text
External Observation Source
  → ShadowTentacle
  → ShadowVesselRuntime.emit()
  → ShadowDigitalSet.append()
  → ShadowStarLayer.yin_project()
  → ShadowGene / RiskGene / CaseGene / IncidentGene
  → ShadowStarLayer.yang_project()
  → ShadowChargeToken / GuardActionCandidate / ReportProjection / ShortCircuitPlan
  → ShadowGate.decide()
  → ShadowVesselRuntime.route_decision()
  → ShadowDigitalSet.append(GateDecision / Result)
  → ShadowStore.commit()
  → Projection: Case / Capsule / Report / Replay
```

T1 的关键词是：

```text
触手采集
血管输送
事实记录
星层压缩展开
Gate 准入
Store 持久化
Projection 派生报告、案例、胶囊、回放
```

---

## 1.2 T1.5 要解决的新问题

T1 解决“怎么记录”和“怎么准入”；T1.5 解决“长期运行后怎么代谢”。

如果没有 T1.5，Shadow Guard 会出现这些问题：

```text
报告越积越多；
Capsule 越积越多；
相似 Case 反复生成重复胶囊；
旧胶囊过时但仍被推荐；
推荐错误胶囊后没有惩罚机制；
CI 产物没有统一保留策略；
Agent / CodeX 跑测试没有统一计划、准入和证据边界；
Mock / Replay / BoardReal 的证据边界仍然可能在报告层被弱化。
```

因此，T1.5 的核心目标是：

```text
让 Shadow Guard 从“会记录的守护系统”升级为“会代谢的工程运行时”。
```


# 3. T1 → T1.5 的核心变化

## 3.1 从 Tentacle Runtime 到 Metabolic Runtime

T1 的中心是：

```text
Tentacle / Vessel / Gate / Store
```

T1.5 新增中心是：

```text
ShadowMetabolism
```

ShadowMetabolism 负责：

```text
报告生命周期；
Artifact 生命周期；
Replay 生命周期；
Case 生命周期；
Capsule 生命周期；
CI 运行产物生命周期；
热度评分；
冷却归档；
逻辑废弃；
审计锚点；
GCPlan 生成；
GCReport 生成。
```

一句话：

```text
T1 负责生成证据；
T1.5 负责管理证据生命周期。
```

---

## 3.2 从 Case/Capsule 生成到 Capsule 版本治理

T1 中 Capsule 是经验沉淀结果。

T1.5 中 Capsule 变成版本化经验资产：

```text
Capsule 不能随便覆盖；
Capsule 可以被 supersede；
Capsule 可以 fork；
Capsule 可以 deprecate；
Capsule 可以 quarantine；
Capsule 推荐失败后必须降权；
Capsule 与 Case / Trace / Environment 建立可追溯关系。
```

---

## 3.3 从“跑测试”到“CI 证据编排”

T1 可以记录测试。

T1.5 要能规划测试：

```text
根据修改文件选择测试；
根据风险级别选择测试；
根据历史失败选择测试；
根据 evidence_type 判断可声明范围；
根据 adapter_mode 防止 Mock 冒充 BoardReal；
根据 CI 产物保留策略归档结果；
把测试过程暴露为 MCP 工具，供 Agent/CodeX 调用。
```

# 5. 核心模块设计

## 5.1 ShadowDigitalSet

定位：

```text
统一事实空间。
```

职责：

```text
保存所有事件；
保存所有 Gate 裁决；
保存所有 CI 运行结果；
保存所有 Capsule 状态变更；
保存所有 GCPlan / GCReport；
保证 trace_id、event_id、route_id 可追溯。
```

T1.5 新增记录：

```cpp
struct ShadowArtifactRecord;
struct ShadowWorkflowRunRecord;
struct ShadowRetentionRecord;
struct ShadowGCPlanRecord;
struct ShadowGCReportRecord;
struct ShadowCapsuleHeatRecord;
struct ShadowCapsuleVersionRecord;
struct ShadowEvidenceClaimRecord;
```

要求：

```text
ShadowStore 仍是事实源；
CaseBank / CapsuleBank / WorkflowIndex 只能是索引；
GC 不允许直接删除事实源；
所有清理行为本身也必须进入 ShadowDigitalSet。
```

---

## 5.2 ShadowMetabolism

定位：

```text
T1.5 的代谢系统。
```

它不是操作系统 GC，而是 Shadow Guard 自己的语义生命周期管理器。

职责：

```text
判断哪些报告可覆盖；
判断哪些 artifact 可删除；
判断哪些 replay fixture 可压缩；
判断哪些 capsule 进入 cold / archived / deprecated；
判断哪些 Store segment 可 compact；
生成 GCPlan；
生成 GCReport；
向宿主 OS 或目标 OS 发出 GC hint，但不把语义决策交给 OS。
```

核心结构：

```cpp
struct ShadowMetabolism {
    RetentionPolicy retention;
    CapsuleHeatPolicy capsule_heat;
    ArtifactPolicy artifact;
    ReplayPolicy replay;
    ReportPolicy report;
    StoreCompactionPolicy store_compaction;
    RiskBudget risk_budget;
};
```

---

## 5.3 ShadowRetentionPolicy

定位：

```text
保留策略。
```

策略对象：

```text
report
artifact
replay
case
capsule
store_segment
workflow_run
gc_report
```

示例：

```yaml
retention:
  reports:
    latest: overwrite
    history_days: 30
    archive_after_days: 30
  artifacts:
    temp_days: 7
    warm_days: 30
    cold_after_days: 90
  replay:
    keep_failed: true
    keep_boardreal: true
    compress_after_days: 14
  capsules:
    cold_after_days: 60
    deprecate_after_conflict: true
  store:
    append_only: true
    compact_allowed: true
    delete_raw_events: false
```

关键原则：

```text
latest 视图可以覆盖；
history 报告可以归档；
artifact 可以删除或压缩；
replay fixture 谨慎压缩；
Capsule 不直接物理删除；
ShadowStore 原始事实不直接删除，只允许 compact / archive / anchor。
```

## 5.4 CapsuleHeat

定位：

```text
胶囊推荐、冷却、归档和废弃的评分系统。
```

热度公式建议：

```text
heat =
  0.25 * recent_hit_score
+ 0.20 * success_score
+ 0.15 * environment_match_score
+ 0.15 * human_confirm_score
+ 0.10 * reuse_score
+ 0.10 * freshness_score
- 0.20 * failure_penalty
- 0.10 * conflict_penalty
```

评分因子：

```text
recent_hit_score：最近是否经常命中；
success_score：使用后是否帮助解决问题；
environment_match_score：环境是否匹配；
human_confirm_score：是否被维护者确认；
reuse_score：是否被多个 Case 复用；
freshness_score：是否适配当前版本；
failure_penalty：推荐失败惩罚；
conflict_penalty：与新证据冲突惩罚。
```

生命周期：

```text
draft
  → active
  → hot
  → warm
  → cold
  → deprecated
  → archived
  → tombstoned
```

状态解释：

```text
draft：由 Case 生成，未经确认；
active：可以推荐；
hot：高频命中，优先推荐；
warm：正常保留；
cold：低频但仍有价值；
deprecated：被新胶囊替代；
archived：归档，不主动推荐；
tombstoned：逻辑删除，仅保留墓碑记录。
```

---

## 5.5 CapsuleVersionGraph

定位：

```text
胶囊版本关系图。
```

为什么需要它：

```text
旧胶囊可能在旧环境下仍然正确；
新胶囊可能只是补充条件；
相似链路不一定是同一根因；
BoardReal 胶囊不能和 Mock 胶囊随便合并。
```

关系类型：

```text
revise：修订；
supersede：替代；
fork：环境分叉；
merge：合并；
deprecate：废弃；
quarantine：隔离；
tombstone：逻辑删除。
```

推荐记录：

```json
{
  "capsule_id": "cap-rk3588-memory-init-001",
  "version": 2,
  "status": "active",
  "relation": {
    "supersedes": ["cap-rk3588-memory-init-001@v1"],
    "derived_from_cases": ["case-rk3588-r3-allocator", "case-rk3588-dtb-memory"]
  },
  "evidence_scope": {
    "adapter_mode": "BoardReal",
    "board_profile": "rk3588-orangepi-5-plus",
    "os_profile": "StarryOS",
    "trace_fingerprint": "..."
  },
  "heat": 0.73,
  "confidence": 0.87
}
```

## 5.6 CapsuleDedup

定位：

```text
防止相似链路反复生成重复胶囊。
```

去重依据：

```text
trace_fingerprint
case_signature
command_signature
adapter_mode
evidence_type
board_profile
os_profile
environment_hash
error_class
last_marker
exit_code
artifact_hash
root_cause_label
```

判定规则：

```text
完全相同 signature：
  不生成新 Capsule，只增加命中和引用。

高度相似但环境不同：
  生成 variant，不合并根胶囊。

根因修正：
  生成 revise / supersede 版本。

结论错误：
  标记 deprecated 或 quarantined。

全新根因：
  生成新 Capsule。
```

## 5.7 ShadowCIWorkflow

定位：

```text
本地 GitHub Actions 类工作流，但增加 Shadow Guard 的证据、准入和保留策略。
```

基本结构：

```yaml
name: sg-t1.5-local-smoke

on:
  event:
    - manual
    - agent_request
    - pre_commit

jobs:
  baseline:
    runs-on: local-wsl
    evidence:
      evidence_type: smoke
      adapter_mode: local
      require_trace_id: true

    gate:
      high_risk_policy: freeze
      allow_remote: false
      allow_board: false

    steps:
      - name: Check profile
        run: shadowguard profile explain

      - name: Build
        run: cmake --build build-wsl -j8

      - name: Test
        run: ctest --test-dir build-wsl --output-on-failure

      - name: Validate plugins
        run: shadowguard plugins validate config/plugins.d

      - name: Generate report
        run: shadowguard report latest

    artifacts:
      collect:
        - build-wsl/Testing/Temporary/LastTest.log
        - reports/latest.md
      retention:
        class: warm
        days: 14

    capsule:
      generate_on_failure: true
      promote_requires_human: true
```

ShadowCIWorkflow 与 GitHub Actions 的区别：

```text
GitHub Actions 关注 workflow / job / step / runner；
ShadowCIWorkflow 还关注 trace_id、evidence_type、adapter_mode、GateDecision、RetentionPolicy、CapsulePolicy、ReplayPlan 和 BoardRealClaimGate。
```

# 6. 设计边界

## 6.1 目标 OS GC 边界

T1.5 不把报告、胶囊、证据交给目标 OS GC 自行处理。

正确模型：

```text
Shadow Guard 生成 GCPlan；
ShadowGate 审批 GCPlan；
宿主 OS / 目标 OS 只接收 GC hint；
文件层面的压缩、移动、删除可以由 OS 执行；
语义决策必须由 Shadow Guard 的 RetentionPolicy 负责。
```

GC hint 示例：

```json
{
  "type": "shadowguard.gc.hint",
  "path": ".shadowguard/reports/archive/",
  "retention_class": "cold_archive",
  "safe_to_compress": true,
  "safe_to_delete": false,
  "reason": "audit_anchor_required"
}
```

禁止：

```text
让目标 OS 自行判断 Capsule 是否没用；
让系统清理工具直接删除 ShadowStore；
让 report 清理破坏 trace_id 引用；
让 artifact 清理破坏 replay 能力；
让 GC 静默发生，不写入 Store。
```

---

## 6.2 Capsule 执行边界

Capsule 是经验资产，不是自动修复动作。

允许：

```text
推荐 Capsule；
解释 Capsule；
根据 Capsule 生成 Plan；
根据 Capsule 生成 Checklist；
根据 Capsule 生成 ReplayPlan；
由用户确认后进入 Gate。
```

禁止：

```text
Capsule 自动修改目标系统；
Capsule 绕过 Gate 执行命令；
Capsule 直接覆盖旧胶囊；
Capsule 把 Mock 经验套到 BoardReal；
Capsule 失败后仍高权重推荐。
```

---

## 6.3 CI 边界

Shadow Guard 不替代 GitHub Actions / GitLab CI / Jenkins。

它做：

```text
本地 workflow 编排；
CI 计划生成；
CI 证据采集；
CI 失败分类；
CI artifact retention；
CI replay plan；
Agent/CodeX MCP 工具层。
```

它不做：

```text
云端 runner 平台；
权限托管；
仓库级云工作流替代；
部署平台替代；
未经 Gate 的远程和板端自动执行。
```

---

## 6.4 Evidence 边界

必须强制区分：

```text
Mock
Replay
QEMU
Linux baseline
StarryOS dry-run
StarryOS native
BoardReal
```

规则：

```text
Mock 不能声明 BoardReal；
Replay 不能声明 BoardReal；
Linux baseline 不能声明 StarryOS native；
QEMU 不能声明 RK3588 实机；
BoardReal 必须有 board_profile、serial_log、artifact_hash、trace_id；
所有 evidence claim 必须通过 EvidenceGate。
```

# 10. 设计模式

## 10.1 Event Sourcing

用途：

```text
所有行为都变成事件；
所有状态可以从事件重建；
GC、Capsule 更新、CI 运行本身也记录成事件。
```

对应模块：

```text
ShadowDigitalSet
ShadowStore
ShadowYinChain
StoreAnchoredShadowChain
```

---

## 10.2 Append-only Log

用途：

```text
保证证据不可随意覆盖；
支持审计；
支持 replay；
支持 hash anchor。
```

对应模块：

```text
events.jsonl
store segment
anchor record
```

---

## 10.3 Policy Engine

用途：

```text
统一准入；
统一风险裁决；
统一 BoardReal 声明检查；
统一 GC 审批。
```

对应模块：

```text
ShadowGate
ActionGate
EvidenceGate
RetentionGate
CapsuleGate
```

---

## 10.4 Adapter / Plugin Pattern

用途：

```text
各种外部来源通过 Tentacle 接入；
插件不直接进入 Store；
远程、构建、主板都按统一协议接入。
```

对应模块：

```text
BreakpointTentacle
PluginTentacle
BuildLinkTentacle
RemoteTentacle
BoardBootTentacle
```

---

## 10.5 Chain of Responsibility

用途：

```text
事件依次经过 Vessel、StarLayer、Gate、Store；
高风险动作被逐层过滤；
不同 Gate 可组合。
```

---

## 10.6 Strategy Pattern

用途：

```text
RetentionPolicy 可替换；
CapsuleHeatPolicy 可替换；
EvidencePolicy 可替换；
WorkflowPolicy 可替换。
```

---

## 10.7 State Machine

用途：

```text
Capsule 生命周期；
WorkflowRun 生命周期；
BoardBoot 状态机；
GCPlan 状态机。
```

---

## 10.8 Repository / Index Pattern

用途：

```text
ShadowStore 是事实源；
CaseBank / CapsuleBank / WorkflowIndex 是可重建索引；
索引可删除重建，不影响事实。
```

---

## 10.9 Command Pattern

用途：

```text
所有执行型行为先封装为 GuardActionCandidate；
再由 ShadowGate 决策；
最后才执行。
```

---

## 10.10 Template Method

用途：

```text
所有 Tentacle 遵循统一 observe → charge → gate → result → store 流程。
```

# 11. 预设算法

## 11.1 Retention Scoring

用于判断对象是否进入 hot / warm / cold / archive。

```text
retention_score =
  value_score
+ evidence_score
+ reference_score
+ freshness_score
- size_penalty
- age_penalty
- duplicate_penalty
```

---

## 11.2 Capsule Heat Scoring

用于胶囊推荐和冷却。

```text
heat =
  0.25 * recent_hit_score
+ 0.20 * success_score
+ 0.15 * environment_match_score
+ 0.15 * human_confirm_score
+ 0.10 * reuse_score
+ 0.10 * freshness_score
- 0.20 * failure_penalty
- 0.10 * conflict_penalty
```

---

## 11.3 Time Decay

用于热度衰减。

```text
decayed_score = base_score * exp(-lambda * age_days)
```

用途：

```text
报告冷却；
Capsule 降权；
Artifact 归档；
WorkflowRun 历史压缩。
```

---

## 11.4 Fingerprint / SimHash

用于判断相似 Case 或 Capsule。

输入：

```text
command_signature
trace_path
error_class
adapter_mode
board_profile
artifact_hash
last_marker
environment_hash
```

输出：

```text
trace_fingerprint
case_signature
capsule_signature
```

---

## 11.5 LRU / LFU 混合策略

用于 artifact 和普通报告，不用于关键 Capsule。

```text
LRU：最近未使用的可冷却；
LFU：长期低频的可归档；
但 BoardReal / audit anchor / human confirmed capsule 不仅按频率删除。
```

---

## 11.6 Graph Supersede Algorithm

用于 CapsuleVersionGraph。

节点：

```text
CapsuleVersion
```

边：

```text
revise
supersede
fork
merge
deprecate
quarantine
```

推荐策略：

```text
优先 active/hot；
避开 deprecated/quarantined；
环境不匹配时选择 variant；
存在 supersede 时优先新版本。
```

## 11.9 Evidence Claim Validation

判断一个报告能声明什么。

规则：

```text
if evidence_type == mock:
    claim_level <= mock_verified

if evidence_type == replay:
    claim_level <= replay_reproduced

if adapter_mode == qemu:
    claim_level <= virtual_hardware_verified

if evidence_type == boardreal:
    require board_profile, serial_log, artifact_hash, trace_id
```

```text
gc_risk =
  reference_count_weight
+ evidence_importance_weight
+ boardreal_weight
+ human_confirmed_weight
- duplicate_weight
- age_weight
- compression_safe_weight
```

# 16. 最终价值

Shadow Guard T1.5 的价值不在于“功能更多”，而在于让系统真正可持续运行。

T1 解决：

```text
看见问题；
记录问题；
准入动作；
生成报告；
沉淀 Case / Capsule。
```

T1.5 解决：

```text
报告怎么清理；
证据怎么归档；
胶囊怎么冷却；
旧经验怎么废弃；
新经验怎么替代旧经验；
CI 结果怎么变成结构化证据；
Agent/CodeX 怎么受控地安排测试；
Mock / Replay / BoardReal 怎么在报告和测试中持续保持边界。
```

最终定义：

```text
Shadow Guard T1.5 是面向复杂 OS / AI Runtime / 边缘设备开发链路的代谢型旁路守护运行时。
它以 ShadowDigitalSet 作为事实空间，以 ShadowVesselRuntime 作为旁路输送，以 ShadowGate 作为准入阀门，以 ShadowStore 作为审计事实源，以 ShadowMetabolism 管理证据、报告、胶囊和 CI 产物生命周期，并通过 MCP 工具层辅助 Agent/CodeX 进行安全、可追溯、可回放的测试编排。
```
